# T43 — Preflight diagnostics and actionable-failure tests

## Assignment

Design unit tests for the preflight path before training or downloading data. The tests should prove that failures are deterministic, actionable, and safe to recover from: missing PyTorch, no usable data, insufficient disk/RAM, and CUDA falling back to CPU.

## Proposed test contract

The eventual preflight implementation should expose a testable function (or CLI adapter) that accepts the run configuration, data/output paths, and injectable environment probes. A result should contain structured diagnostics rather than requiring tests to parse arbitrary log text. Each diagnostic should have at least:

- stable `code` (for example `TORCH_MISSING`, `DATA_MISSING`, `DISK_LOW`, `RAM_LOW`, `CUDA_FALLBACK`);
- `severity` (`error`, `warning`, or equivalent);
- a concise human-readable message;
- an actionable `remediation` (what the user should install, download, free, or change);
- relevant facts such as path, required bytes, available bytes, requested device, and selected device.

The CLI adapter should return a non-zero status for blocking errors, zero for a runnable CPU fallback, and should not start training or create a partial checkpoint when preflight blocks. Exact names may be adapted to the implementation, but the assertions below should remain observable and stable.

## Unit-test matrix

Use a temporary directory and fake/injected probes. Do not uninstall packages, allocate large arrays, fill a disk, or depend on the host GPU. Each test should assert the diagnostic code and structured facts, not the complete wording of a message.

### 1. Missing PyTorch is an actionable blocking failure

Suggested test: `test_preflight_missing_torch_reports_install_action`.

1. Inject an import probe that raises `ModuleNotFoundError` for `torch` (or inject the dependency-check result if the implementation separates probing from reporting).
2. Run preflight with an otherwise valid temporary data/output setup.
3. Assert exactly one blocking torch diagnostic, with `severity=error`, a non-zero/blocked result, and remediation naming the supported environment/dependency installation path.
4. Assert the diagnostic does not expose a traceback or suggest that CPU fallback can repair a missing framework.
5. Assert no training callback, dataset loader, checkpoint writer, or CUDA probe is invoked after this blocking dependency failure.

Also cover a generic import exception separately if the implementation distinguishes it: report the import failure and remediation, rather than silently treating an unrelated broken installation as a healthy CPU-only environment.

### 2. Missing or empty data is an actionable blocking failure

Suggested tests: `test_preflight_missing_data_reports_path_and_remediation` and `test_preflight_empty_data_is_not_runnable`.

- Point the data root at a nonexistent path. Assert a `DATA_MISSING`/equivalent error, the normalized path in facts, a remediation explaining the required Churn dataset/provenance, and a blocked result.
- Point the data root at an existing but empty temporary directory (or a directory containing no recognized split files). Assert a data error rather than success, and include the expected file/split shape in remediation.
- Ensure a directory containing unrelated files is not accepted merely because it exists.
- Assert no synthetic data is silently generated and no download begins as an implicit side effect of preflight. If download is an explicit command, remediation may point to that command.

If the project validates train/validation/test splits, add a parametrized case for each missing split and assert the missing split name in structured facts. The test should not require a network connection.

### 3. Insufficient disk space is deterministic and non-destructive

Suggested test: `test_preflight_low_disk_reports_required_and_available_bytes`.

Inject a disk-usage probe returning a controlled `available_bytes` below the calculated requirement (include a small safety margin if the implementation has one). Assert a blocking `DISK_LOW`/equivalent error with numeric required and available values, the affected output/data path, and remediation to free space or choose another location. Assert no files are created and no write/training callback runs.

Boundary parametrization should cover:

- available exactly equal to the requirement: runnable (unless the documented policy is strictly greater);
- available one byte below: blocked;
- probe failure/unknown usage: a clear diagnostic or documented conservative behavior, never an uncaught exception.

Use the same byte units in facts and assertions; avoid testing localized formatting. Do not use actual free-space exhaustion.

### 4. Insufficient RAM is deterministic and does not allocate memory

Suggested test: `test_preflight_low_ram_reports_requirement_and_remediation`.

Inject a memory probe returning a controlled available/total memory value below the estimated requirement for the configured batch, member count, and dtype. Assert a blocking `RAM_LOW`/equivalent error, numeric required and available facts, and remediation such as reducing batch/members or closing applications. Assert no model construction, tensor allocation, dataloader worker creation, or training callback occurs.

Boundary parametrization should cover exactly-at-threshold and one-byte-under-threshold values. If the implementation cannot reliably distinguish host available RAM from total RAM, assert the documented metric consistently and label it in facts. Probe exceptions should yield a controlled diagnostic rather than an unhandled error.

### 5. Requested CUDA falls back safely to CPU

Suggested tests: `test_preflight_cuda_unavailable_falls_back_to_cpu` and `test_preflight_cuda_runtime_error_falls_back_to_cpu`.

With PyTorch import available, inject `cuda.is_available() == False` while configuration requests CUDA. Assert:

- preflight remains runnable (no blocking error);
- a warning diagnostic with `CUDA_FALLBACK`/equivalent code records requested `cuda` and selected `cpu`;
- remediation explains that training will run on CPU and how to install/enable a compatible CUDA build if GPU execution is wanted;
- the resolved device is exactly CPU and is passed to the downstream run;
- training is invoked once with CPU, without a second attempt to initialize CUDA.

Repeat with a probe/device-construction error (for example, CUDA reported available but `torch.device("cuda")` or a minimal CUDA capability check raises). This must follow the documented fallback policy and retain the original failure as a diagnostic fact; it must never claim CUDA was selected. If configuration has a strict/no-fallback mode, add the complementary test asserting a blocking CUDA diagnostic and non-zero status in that mode.

### 6. Diagnostic aggregation and precedence

Suggested test: `test_preflight_aggregates_independent_failures_without_side_effects`.

Inject missing data, low disk, and low RAM together (with torch present) and assert all independently discoverable diagnostics are returned in stable code order. The result is blocked, remediation is present for each issue, and no training begins. A missing torch case may short-circuit checks that require torch; if so, assert the documented precedence and ensure the response explicitly says which checks were skipped rather than reporting false success.

Use a stable ordering rule (severity then check order, or explicit check order) so CLI and snapshot output do not flap between runs. If diagnostics are serialized, assert JSON serializability and that paths/facts contain no secrets.

## Test doubles and fixtures

- `tmp_path`: valid and invalid data/output roots; all paths are workspace-local and disposable.
- `FakeEnvironment`: import, disk, RAM, CUDA availability, and device probes with call counters.
- `run_started`/`write_started` spies: prove blocking preflight has no training or filesystem side effects.
- A minimal valid synthetic fixture only where the data validator needs a positive control; never use it as an implicit fallback for a missing real dataset.
- `monkeypatch` or dependency injection for `importlib`, `shutil.disk_usage`, memory lookup, and torch CUDA/device calls. Keep each test independent and restore patches automatically.

## Acceptance criteria for the eventual tests

The suite should run without GPU, network, large memory, or special filesystem permissions. Every blocking failure names a stable code, affected resource, observed/required values where applicable, and a concrete next action. The CUDA test proves the selected device used by execution, not merely a warning string. Tests must fail if preflight raises raw `ModuleNotFoundError`, silently accepts an empty data directory, performs real resource exhaustion, silently substitutes synthetic data, or proceeds into training after a blocking error.
