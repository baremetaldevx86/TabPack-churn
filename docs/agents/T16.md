# T16 — Pure greedy ensemble selector design

## Assignment and scope

Define a small, pure, deterministic selector for binary validation
probabilities. It must aggregate selected candidates by probability averaging,
score every proposed aggregate with validation ROC-AUC, accept only strict
improvements, never select one candidate snapshot twice, and make all ties
reproducible. This is an API/algorithm/test contract for the eventual
implementation owner; no source module, dependency, checkpoint, or training run
was added by T16.

## Evidence and coordination inputs

I read `swarm.md` before starting and reviewed the available related notes:

* **T17:** binary ROC-AUC must reject empty or single-class labels and malformed
  values; cross-class score ties receive half credit. The selector must pass
  averaged probabilities to that strict metric and propagate its errors.
* **T35:** selection is training state. Candidate IDs must include snapshot
  identity, prediction caches may be retained for replay, and candidate order,
  full-precision scores, selected snapshots, and validation-only state belong in
  the checkpoint.
* **T36:** preserve exact score ties, avoid rounding before comparison, and use
  stable/full-precision probability averaging at the metric boundary.
* **T47:** validation selection is adaptive and therefore optimistic; test
  labels/predictions must not enter this API. Test evaluation follows a frozen
  selection result and all prespecified seeds are reported.

## API contract

The implementation should expose immutable value objects similar to:

```python
@dataclass(frozen=True)
class Candidate:
    candidate_id: str       # unique snapshot ID, e.g. "member-02@epoch-17"
    member_id: str          # base lineage; may repeat at different epochs
    source_epoch: int
    probabilities: tuple[float, ...]  # positive-class p, in validation row order


@dataclass(frozen=True)
class SelectionStep:
    round_index: int
    candidate_scores: tuple[tuple[str, float], ...]
    winner_id: str | None
    accepted: bool
    resulting_auc: float


@dataclass(frozen=True)
class SelectionResult:
    selected: tuple[Candidate, ...]
    validation_auc: float
    candidate_order: tuple[str, ...]
    steps: tuple[SelectionStep, ...]
    validation_evaluations: int
    stop_reason: str


def greedy_select(
    y_validation: Sequence[int],
    candidates: Sequence[Candidate],
    *,
    max_size: int,
    initial_selected: Sequence[Candidate] = (),
) -> SelectionResult:
    """Select a validation-AUC-improving probability-average ensemble."""
```

The concrete module and import path are left to the coordinator. The public
function should use the project's strict `binary_roc_auc` implementation, not a
second metric implementation. `y_validation` and every candidate probability
sequence are ordinary detached one-dimensional sequences in the same sample
order. A tensor-producing caller should detach/copy predictions before calling
this pure boundary.

Input validation should fail loudly with `ValueError` (or the project's one
established validation exception) for:

1. empty, unequal-length, nonbinary, or single-class `y_validation`;
2. `max_size < 0`, a non-integral `max_size`, or more initial snapshots than
   `max_size`;
3. duplicate `candidate_id` values in either input sequence, or an ID occurring
   in both `initial_selected` and `candidates`;
4. candidate probabilities with a wrong length, nonfinite values, or values
   outside `[0, 1]`; and
5. invalid snapshot metadata such as an empty/non-string ID or a negative epoch.

Use a finite `0.5` baseline for an empty ensemble: it is the ROC-AUC of a
constant no-information positive-class predictor. Thus an empty initial set is
returned when no candidate has AUC strictly greater than `0.5`. This makes
strict improvement well-defined for the first addition; a caller that requires
at least one member must state and validate that separate protocol constraint,
rather than silently accepting a non-improving model.

`initial_selected` is for an online epoch call that resumes an already selected
snapshot set. Its IDs are considered consumed. The caller should pass the
current-epoch candidates plus any unselected eligible snapshots; a previously
selected snapshot must not also appear in `candidates`. Repeated `member_id`
values are allowed when `candidate_id`/`source_epoch` differ, as required for
different checkpoints of one base member. “Without replacement” is therefore
about immutable candidate snapshot identity, not base-member lineage.

## Deterministic ordering and tie policy

Each candidate must have a stable ID independent of Python object identity,
memory address, process order, or a filename that can change between runs. Use
the canonical key `(candidate_id, member_id, source_epoch)` and sort the pool by
that key before any comparisons. Since `candidate_id` is unique, this produces
one order even if the caller supplies candidates in a different order. Record
that order in `SelectionResult.candidate_order` and in the checkpoint.

At each greedy round, compute a prospective AUC for every remaining candidate.
Choose the highest prospective AUC. If multiple candidates have exactly the
same prospective score, use the candidate's individual validation AUC as the
second key (higher is preferred), then the lexicographically smallest canonical
key. The individual AUC is computed from that candidate's own probabilities,
not from a member ID or a training loss. This mirrors the pinned online greedy
semantics while making the final fallback independent of incidental pool order.
Compare the winner's full-precision prospective score to the current score with
exact `>`; do not use `>=`, rounding, or an arbitrary tolerance. A tied or
lower-scoring winner is not selected, and the round terminates because every
other remaining candidate is no better than the winner. Candidate scores are
retained in the step trace for audit/replay, including the rejected final
round.

The candidate order is an explicit protocol field, not incidental list order.
The stable IDs also make a tie reproducible across processes and make a replay
independent of a hash/randomized dictionary iteration order.

## Algorithm

Let `S` be the immutable selected tuple and let `P(S)` be the per-row
arithmetic mean of its positive-class probabilities. For `S = ()`, use the
constant vector `0.5` only for the baseline score. Probability averaging must
be performed before ROC-AUC; do not average member AUCs and do not average
logits in place of probabilities. A host-side `math.fsum` or an explicitly
documented float64 accumulator is appropriate for each row so that accumulation
order does not create avoidable tie changes.

```text
validate y_validation, candidates, initial_selected, and max_size
remaining := candidates sorted by (candidate_id, member_id, source_epoch)
selected := immutable copy of initial_selected
if selected is empty:
    current_auc := 0.5
else:
    current_auc := binary_roc_auc(y_validation, average_probabilities(selected))

while len(selected) < max_size and remaining is not empty:
    scored := []
    for c in remaining:
        p := average_probabilities(selected + (c,))
        score := binary_roc_auc(y_validation, p)
        individual_score := binary_roc_auc(y_validation, c.probabilities)
        scored.append((score, individual_score, canonical_key(c)))

    winner := item with maximum score, then maximum individual_score,
              then minimum canonical_key
    append all (candidate_id, score) values in canonical order to the trace
    if winner.score <= current_auc:       # exact comparison
        stop with "no_strict_improvement"
    selected := selected + (winner.candidate,)
    remove winner.candidate_id from remaining
    current_auc := winner.score

return selected, current_auc, trace, "max_size" or "pool_exhausted"
```

The implementation may cache each candidate's detached validation predictions
and each `(selected IDs, candidate ID)` evaluation within one call, but the
cache must not mutate input objects or be reused across changed labels. T35's
checkpoint layer may persist equivalent immutable prediction caches for resume;
the selector itself remains a pure function of its arguments.

### Invariants

* `selected` is ordered by acceptance round and contains unique candidate IDs.
* Every accepted candidate came from the supplied pool or immutable initial
  state, and no candidate ID is removed and then reinserted.
* `validation_auc` is the AUC of the probability average of exactly `selected`
  (or `0.5` for empty selection).
* After a non-improving round, no remaining candidate can satisfy strict
  improvement, because the winner was the maximum prospective score.
* Repeating the call with equal values and the same stable IDs returns the same
  selected IDs, scores, and trace, regardless of input candidate order.
* No test labels, test probabilities, or test metric is accepted by this API.

For a pool of `K` candidates, validation size `N`, and selected limit `L`, the
straightforward implementation costs at most `O(L K N log N)` due to repeated
ROC-AUC sorting and `O(KN)` prediction storage. The reduced protocol has small
`K` and `L`; correctness and replayability are preferred over a more complex
incremental AUC data structure.

## Focused tests

The implementation owner should add tests at the selector boundary (using the
real strict binary AUC metric) for the following cases:

1. **Best first candidate:** two candidates with AUCs `0.75` and `0.625` select
   the former, and the result score equals AUC of its probabilities.
2. **Probability averaging:** a second candidate is accepted only when the
   row-wise average of the first two has a strictly higher AUC; assert the
   result is not the average of per-candidate AUCs and not an average of logits.
3. **Strict rejection:** a candidate whose aggregate AUC equals the current
   AUC is not selected; a candidate with a lower score is not selected. Include
   an all-tied pool and assert that the result is empty when every singleton is
   `0.5` or below.
4. **Deterministic ties:** candidates with equal prospective AUCs select the
   smallest canonical key. Run with the candidate sequence in several shuffled
   orders and compare the complete selected-ID/trace result.
5. **Without replacement:** with `max_size=3`, assert no selected ID repeats;
   duplicate IDs raise. Permit two snapshots with the same `member_id` but
   different epochs and verify they can be selected as distinct candidates only
   when each accepted aggregate strictly improves.
6. **Initial online state:** pass an initial selected snapshot and a pool that
   includes a better current-epoch candidate plus an already-selected ID; assert
   the duplicate is rejected and only the unselected strict improvement is
   added. Also assert the initial score is recomputed from averaged probabilities.
7. **Limits and purity:** `max_size=0`, an empty pool, `max_size=1`, and a pool
   smaller than the limit return the documented stop reason. Snapshot input
   tuples/lists remain unchanged, and two calls return equal immutable results.
8. **Validation failures:** propagate the T17 single-class/empty/mismatched
   label errors; reject duplicate IDs, wrong lengths, NaN/Inf, and probabilities
   outside `[0, 1]`.
9. **Metric ties and precision:** use equal probabilities across classes to
   confirm half-credit AUC behavior, and ensure no rounded score is used for the
   strict comparison or tie decision.

Tests should use tiny hand-computable arrays and an exhaustive small-pool oracle
where practical. They must not download data, instantiate models, evaluate test
labels, or run training.

## Integration advice and coordination

* **T14/T15:** expose detached validation probability snapshots with stable
  member/epoch identity. The selector should consume snapshots, not live model
  objects or mutable parameter references.
* **T17:** keep one canonical binary ROC-AUC implementation. The selector should
  propagate its undefined-metric exception and never substitute `0.5` for a
  single-class validation split; `0.5` is only the explicitly defined empty
  ensemble baseline after labels have passed validation.
* **T19/T18:** preflight must verify both validation classes and identical row
  ordering before selection. Preprocessing and label fitting remain outside this
  pure function.
* **T23:** implement the focused tests above, especially input-order invariance,
  exact strictness, duplicate snapshot IDs, and same-member/different-epoch
  behavior. T23's note was not available when this note was completed; please
  flag any disagreement about the empty-ensemble baseline or tie key.
* **T35/T20:** persist candidate order, selected IDs, source epochs, full
  precision AUCs, per-round candidate scores/evaluation count, and stop reason.
  Evaluate test metrics only after this result is frozen.
* **T47/T29/T32:** label validation optima as selection-optimistic and report
  post-freeze test scores for all prespecified seeds; do not use this selector's
  validation trace to claim an unbiased validation estimate.
