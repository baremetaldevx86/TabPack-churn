# T36 — Numerical stability review

## Assignment and scope

Review the reduced Churn-only protocol for numerical failure modes in mixed
categorical/numeric preprocessing, sigmoid/log-loss evaluation, ROC-AUC,
CUDA/CPU execution, and the mandated float32 training dtype. This is a design
review only. The checkout had no implementation or test files when this note
was written, so no source or long-running experiment was added.

## Findings and recommendations

### 1. Mixed numeric/categorical preprocessing

1. Keep numeric and categorical branches separate until both are transformed.
   Fit one composite preprocessor on train rows only, then reuse it for
   validation and test. Never fit a transformer, imputer, or category list on
   a holdout, even if a holdout contains a missing or unknown value.
2. Numeric contract: validate raw numeric columns for finite non-missing values
   (reject `+/-inf` rather than allowing it into an estimator), impute missing
   values with train medians, then fit the quantile-normal transform on those
   imputed train values. `QuantileTransformer(output_distribution="normal")`
   is non-linear and maps values outside the fitted range to finite output
   bounds; it must not be refit to expose holdout ranges. If a train numeric
   column has no observed value, fail preflight because its median is
   undefined rather than borrowing a holdout value.
3. `QuantileTransformer` disregards NaNs during fit and preserves NaNs during
   transform. Therefore impute before it, and assert that transformed arrays
   contain no NaN. Also assert finite output after the transform; do not use a
   blanket `nan_to_num` fallback that could hide a broken fitted state.
4. Categorical contract: impute missing values with the train-fitted
   most-frequent category, then fit one-hot encoding on train categories only
   with unknown handling equivalent to `handle_unknown="ignore"`. An unknown
   holdout category must produce an all-zero vector in its feature block and
   must not change category order, feature names, or output width. If a train
   categorical column has no observed category, fail preflight instead of
   deriving a mode from validation/test.
5. Use an explicit dense numeric output for the MLP and cast the final feature
   matrix once to `np.float32` (then `torch.float32`). Scikit-learn transformers
   commonly produce float64 by default, while one-hot output is commonly
   float64 unless `dtype=np.float32` is requested. Avoid concatenating a
   float64 branch with a float32 branch and relying on an implicit, potentially
   device-dependent cast.
6. At the train-transform, holdout-transform, tensor-transfer, and model-input
   boundaries check shape, dtype, and `isfinite`. Preserve a feature-schema
   fingerprint (ordered numeric names, category names, and output width) and
   the train-fitted imputer/quantile/encoder state in provenance. This directly
   addresses the sentinel and state-invariance tests proposed by T24.

### 2. Sigmoid and binary log-loss

1. Produce logits from the model and train with
   `torch.nn.functional.binary_cross_entropy_with_logits` or
   `nn.BCEWithLogitsLoss`; do not call sigmoid before the loss. PyTorch combines
   sigmoid and BCE with a log-sum-exp implementation that remains finite for
   very large positive/negative logits. A hand-written
   `-y*log(sigmoid(x))-(1-y)*log(1-sigmoid(x))` is vulnerable to `log(0)` and
   should not be used for training.
2. For packed logits with shape `[members, batch]` and targets `[batch]`,
   expand targets across members, compute unreduced BCE, mean over samples for
   each member, and sum those member means. This is the local protocol's
   reduction. A global `reduction="mean"` over both members and samples would
   divide the gradient by the member count and silently change the experiment.
3. Use float32 logits, targets in `{0,1}`, and parameters in float32 during
   training. Do not add an epsilon to logits or clamp logits before
   `BCEWithLogitsLoss`; both alter the objective. Check logits, loss, gradients,
   and optimizer state for finiteness after each update (or at least each
   epoch in a fast mode). A non-finite value should stop the run with member,
   epoch, and batch diagnostics, rather than be silently clipped.
4. For log-loss reporting from logits, prefer a stable logit-space expression
   such as `softplus(logit) - target * logit`, accumulated in float64 on the
   host if the reporting path permits it. If reporting from probabilities (for
   example, the mandated probability-averaged ensemble), cast to float64 before
   averaging and apply a documented finite-bound clip only at the metric
   boundary. Do not use the float32 `1 - p` followed by `log` for saturated
   probabilities.

### 3. ROC-AUC and score saturation

1. Validate that every validation/test split used for binary ROC-AUC contains
   both labels. If not, fail with an explicit split/label-count diagnostic;
   do not substitute 0.5 and do not use test labels to repair a validation
   split.
2. ROC-AUC consumes scores, not thresholded classes. A sigmoid is mathematically
   monotone, but float32 sigmoid saturates: in the local smoke check logits 20
   and 21 both became exactly `1.0`, while float64 sigmoid preserved their
   order. Therefore never compute AUC from `torch.sigmoid(logits.float())` when
   raw logits are the available score. For a single model/candidate, detached
   raw logits are the most stable ranking score.
3. The protocol requires probability averaging for ensembles. Preserve that
   semantics while avoiding avoidable ties: move detached logits to CPU,
   convert to float64, apply sigmoid in float64, accumulate the member
   probabilities in float64, and then pass the averaged probabilities to the
   binary AUC implementation. This changes only metric/evaluation precision,
   not model training dtype. Record the metric dtype. If the implementation
   intentionally evaluates in float32, record the resulting saturation/tie
   behavior and test it explicitly.
4. Keep metric inputs in sample order and assert their length matches labels.
   Check for NaN/Inf before calling `roc_auc_score`; preserve exact score ties
   because the metric's tie handling is part of the reported result. Do not
   round predictions or AUC values before strict-improvement greedy selection.
   Store the full-precision validation score and deterministic candidate order,
   consistent with T35's checkpoint requirements.

### 4. CUDA/CPU behavior and reproducibility

1. Resolve one device at run start (`cpu` or the requested CUDA device), move
   model, batches, and targets explicitly to it, and record the resolved
   device plus PyTorch/CUDA versions. An unavailable explicitly requested CUDA
   device should produce a clear preflight error; silently falling back to CPU
   changes the run and its timing/resource claim.
2. Keep autocast, AMP, and gradient scaling disabled for the reduced float32
   protocol. Assert model parameters, input tensors, logits, and targets are
   float32 during training. Metric accumulation may use host float64 only when
   explicitly documented as above.
3. PyTorch does not guarantee bitwise equality between CPU and GPU, even with
   identical inputs and seeds. Packed-vs-independent equivalence tests should
   compare on the same device with predeclared float32 tolerances; a CPU/GPU
   cross-check should be a finite/value-level smoke test, not a bitwise
   trajectory test. Floating-point addition is not associative, so packed
   reductions, per-member loops, and different BLAS/CUDA kernels can differ by
   small amounts.
4. For a strict reproducibility/debug mode, seed Python/NumPy/PyTorch as
   required by T34, use explicit per-member generators, disable cuDNN
   benchmarking, and enable deterministic algorithms where supported. This may
   be slower or raise on an operation without a deterministic CUDA kernel.
   Record whether strict mode was enabled. DataLoader worker and sampler state
   must be controlled; changing batch order changes float32 reduction order.
5. Set the CUDA TF32 policy explicitly and record it. For an IEEE-like
   float32 protocol, use the PyTorch-version-appropriate setting that disables
   TF32 for matmul (and convolution if ever introduced); on older releases the
   compatibility setting is `torch.backends.cuda.matmul.allow_tf32 = False`,
   while newer releases expose `fp32_precision="ieee"`. Also use the highest
   available float32 matmul precision setting. Do not mix a TF32-enabled GPU
   run with an IEEE CPU baseline without labeling the difference.
6. No CUDA OOM or non-finite recovery should silently restart on another device
   or change dtype. Emit a diagnostic and require a new, explicitly recorded
   run configuration. Synchronize CUDA only for timing/profiling, not in every
   training step merely to make asynchronous execution appear deterministic.

### 5. Float32-specific guardrails

* Treat float32 as an intentional protocol choice, not an implementation
  accident. It has roughly seven decimal digits of precision, and repeated
  member reductions can accumulate rounding error. Keep gradients and updates
  in float32, but use float64 for small host-side probability sums and final
  scalar reporting when the exact protocol permits it.
* Avoid constructing tensors from Python/NumPy float64 values without an
  explicit dtype. Avoid in-place mixed-dtype arithmetic and implicit CPU/GPU
  copies in metric code.
* Assert finite values at each phase boundary and log min/max (not complete
  private data) for transformed features, logits, probabilities, loss, and
  gradient norms. The diagnostic must distinguish a preprocessing failure from
  an optimizer/model overflow.
* Do not claim CPU/GPU bitwise reproducibility or exact rerun identity across
  PyTorch releases. Results should include device, backend precision policy,
  model dtype, metric dtype, seed, and deterministic-algorithm setting.

## Minimal acceptance checks for integration

1. A preprocessing fixture with train-only medians/categories and extreme
   holdout sentinels yields identical fitted train state when holdout rows are
   changed; all three transformed splits have the same finite float32 schema.
2. A logits fixture containing values such as `[-1000, -100, 0, 100, 1000]`
   yields finite BCE-with-logits loss and gradients, while a manually sigmoid-
   then-log implementation is rejected or demonstrably less stable.
3. A ranking fixture with logits `[20, 21]` verifies that metric evaluation
   does not collapse their order through float32 sigmoid saturation. AUC input
   with one class is rejected explicitly.
4. The packed loss test verifies member means are summed, not globally
   averaged, and checks finite outputs/gradients on both CPU and available CUDA
   using the same dtype. CPU/GPU comparisons use tolerances and do not require
   bitwise equality.

## Tests run

* Ran a short, dependency-free Python smoke check with Python 3.12.10,
  NumPy 2.5.3, and PyTorch 2.11.0+cu128. `BCEWithLogitsLoss` remained finite
  with logits through +/-1000 and had finite gradients.
* The same check demonstrated the AUC hazard: float32 sigmoid mapped logits
  20 and 21 to `[1.0, 1.0]`, while float64 sigmoid retained distinct values.
* No project tests or training were run. scikit-learn is not installed in the
  current environment, so the scikit-learn behavior above is from its official
  API documentation rather than a local execution.
