# T4 — Paper evaluation protocols and fair reductions

## Assignment and conclusion

Research the paper's evaluation protocols and define an honest reduced Churn comparison among an ordinary MLP, a homogeneous independent MLP ensemble, and a heterogeneous packed TabPack-style ensemble.

**Recommendation:** use the ledger's three-seed, four-member experiment as a **reduced, fixed-recipe workflow comparison under the paper's optimistic multi-seed protocol**. It can compare these three locally specified recipes on canonical Churn. It does not reproduce the paper's conservative evaluation, isolate the benefit of heterogeneity or packing, or establish a general speed/accuracy advantage.

## Fair reduced experiment contract

### Three clearly named methods

1. **Ordinary MLP:** one independently initialized, fixed depth-2/width-64/dropout-0.1 MLP; AdamW learning rate 0.001 and weight decay 0.0001. Save the best validation-ROC-AUC checkpoint under the prespecified stopping rule.
2. **Homogeneous independent MLP ensemble:** four independent MLPs with exactly that baseline configuration; separate weights, optimizer states, initialization/dropout streams, and training permutations. Uniformly average their positive-class probabilities. Recommended simple checkpoint rule: evaluate the four-member mean after each common epoch and retain the best ensemble checkpoint. If instead members stop/checkpoint individually and are combined afterwards, explicitly label this offline construction and record individual epochs; do not silently mix these definitions.
3. **Reduced heterogeneous packed TabPack-style ensemble:** four independent randomly configured MLPs in a pack, using the ledger's smaller depth/width/dropout/AdamW ranges. After each epoch greedily rebuild from current states plus the prior selected snapshots, using validation ROC-AUC and strictly improving additions without replacement, at most four selected snapshots. Freeze the best validation-selected ensemble before test inference. Different snapshots of one member can be selected; four selected snapshots need not represent four unique member IDs.

All are plain MLP-family methods without periodic embeddings or weight sharing. The homogeneous baseline is neither TabM (which has additional method-specific design) nor paper SameHP (which retains TabPack machinery and tunes the shared hyperparameters).

### Shared controls

- Use exactly the same canonical splits, feature availability, target coding, and train-fitted preprocessing for all methods. One prepared transform per prespecified repeat, shared across methods, avoids method-specific preprocessing randomness. The test set cannot drive imputations, feature decisions, thresholds, checkpointing, or parameter choices.
- Freeze seed list `[0, 1, 2]`, member distributions, epoch cap 100, patience convention, batch size 256 **per member**, float32, metric definitions, tie rules and checkpoint policies before testing. In the paper stopping occurs after `patience + 1` non-improving epochs; record whether the reduced implementation uses that convention or `patience` directly.
- No external hyperparameter tuning for any local method. Nevertheless, the heterogeneous method still performs within-run hyperparameter exploration and adaptive validation selection; “no tuning” does not mean equal search opportunity.
- Aggregate losses by first averaging over each member's samples and then summing across members, rather than training an averaged prediction. Use independent batches/permutations, not a shared member optimizer state. The homogeneous and packed implementations must retain independent learning dynamics.
- Average probabilities for ensemble prediction; compute metrics on that mean. Do not average per-member AUCs or average logits and call the result the same ensemble.
- Define a run as one method plus one prespecified experiment seed. The internal four members are not four statistical replications. Save actual sampled configurations and derived seeds so repetitions are unambiguous.

## What “fair” means here—and what it cannot mean

**Common recipe limits are not equal compute.** The single MLP gets one trajectory; ensembles get four, and heterogeneous models have different capacities and padded execution costs. Equal epochs and per-member batch sizes are transparent common controls, not parameter-, FLOP-, wall-clock-, or validation-search-matched budgets. Report realized epochs, active parameter counts, padded/storage parameter counts, selected size, unique selected member count, and runtime rather than claiming matched resources.

**The three-way comparison measures complete workflows.** Relative to ordinary MLP, the homogeneous ensemble changes model count and checkpoint selection. Relative to the homogeneous ensemble, reduced TabPack changes hyperparameters, capacity, packing, and snapshot/greedy selection. Any score difference cannot be attributed solely to hyperparameter diversity; any runtime difference cannot be attributed solely to packing.

If a later study needs causal attribution, it should separately compare (a) identical candidate configurations trained packed versus independently with identical selection, and (b) homogeneous versus heterogeneous candidates under identical selection. Those are useful future ablations, not unrequested additions to the small three-method run.

**Timing must compare local work with local work.** Record full run wall time including training, validation, checkpoint handling, and ensemble selection with consistent boundaries; report preprocessing/test-inference time separately or explicitly include them for every method. Synchronize CUDA before/after timed regions. Show per-seed times and their aggregate plus total study compute. The paper's headline compares baseline tuning time with TabPack main-run training time; do not transplant those speedup claims to this no-tuning Windows/laptop/CPU experiment. A small CPU pack may be slower despite mathematical equivalence.

## Reporting and explicit caveats

- Report all three per-seed test ROC-AUC values, arithmetic mean and **sample** SD (`ddof=1`), plus prespecified secondary metrics such as log loss. Never pick the best seed or pool predictions across seeds unless that extra ensemble is explicitly a different method.
- Provide paired per-seed method differences when run mapping is predeclared. Three seeds describe algorithmic variability on one fixed dataset/split; they do not measure uncertainty over new data splits or datasets and cannot support strong significance/generalization claims.
- Call independently repeated full TabPack runs **optimistic protocol**, using the paper's terminology. This describes repeated candidate exploration versus fixed selected configurations; it does not itself mean that an untouched final test metric was selected or leaked. Separately disclose adaptive validation reuse.
- Distinguish hard epoch-cap termination from genuine patience termination. A cap-hit method may be undertrained; dropping or rerunning only an unfavorable capped seed biases the comparison.
- Canonical data with changed optimizer, member counts, widths, sampling spaces, patience, batch size, preprocessing, pruning, embeddings, and evaluation protocol still yields a reduced experiment. Matching one published Churn number would not establish reproduction.
- One Churn task cannot establish the paper's across-dataset ranking or out-of-the-box generality. Failure to beat the fixed homogeneous ensemble is a valid result, not grounds to retune against the test set.

Suggested final wording:

> We compare three prespecified small MLP-family workflows on the canonical Churn split with three seeds. Reduced TabPack-style results use the optimistic protocol: each seed repeats candidate sampling, training, and validation-only online selection. All test predictions are produced after freezing checkpoints/ensembles. The methods share preprocessing, epoch limits, and per-member batch size but are not compute- or capacity-matched. We report every seed and mean ± sample SD; these are exploratory reduced results, not a reproduction of the paper's conservative benchmark.
