The report is careful about the main scientific claim boundary: it labels the

## Findings

### F1 — High: `ReducedConfig.dtype` is accepted and recorded but ignored

`ReducedConfig` accepts both `float32` and `float64` (`tabpack/core.py:217-218`),
while the runner hard-codes float32 in the environment record and ordinary
constructor (`tabpack/experiment.py:99-114`, `179-188`), probability inputs
(`154-168`), ordinary training tensors (`205-206`), homogeneous tensors
(`286-287`), and packed construction/training/validation (`345-365`,
`393-397`).  A caller can therefore serialize a float64 config and silently
execute float32 computation.  This is a reproducibility and numerical-policy
failure, not merely an unimplemented option.

**Minimal fix:** map the resolved config dtype to one torch dtype and use it
for every model, feature/label tensor, probability path, and environment
field; reject unsupported dtypes at the runner boundary.  Add a tiny
float64 smoke/integration assertion that the model parameters, input tensors,
and manifest all agree.  If float64 is intentionally removed, reject it in
`ReducedConfig` and remove it from the documented API rather than silently
coercing it.

### F2 — High: reported fit timing is not the stated complete workflow timing

The fit timers begin only after model and optimizer construction:
ordinary (`tabpack/experiment.py:254-258`, timer `214`), homogeneous
(`272-292`), and packed (`345-375`).  Consequently initialization and
optimizer construction are omitted from `fit_wall_s`, while packed snapshot
extraction/selection is included.  The report table labels this value “Fit
seconds” (`reports/churn-reduced/report.md:9-13`), but the checkpoint note calls
the values “complete workflow timings” (`docs/checkpoints.md:56-59`).  The
method loop is also fixed in `METHODS` order (`experiment.py:43-47`,
`562-575`), with no recorded order or timing warm-up policy.  The one-shot
test prediction is separately timed, but is not a throughput benchmark.

**Minimal fix:** choose and state one boundary.  For a workflow comparison,
start the same timer before model/optimizer construction for every method and
report the exact scope; alternatively rename the current value
`train_validate_select_wall_s` and publish `run_wall_s` as the complete cost.
Record method order, CUDA synchronization/warm-up policy, and whether
checkpoint serialization is included.  Do not infer a packing speedup from
the current table; the existing caveat is appropriate until this is fixed.

### F3 — High: interruption/partial-run lifecycle is not finalized

`run_comparison` writes an initial manifest (`tabpack/experiment.py:544-561`)
and only adds `finished_at_utc` after every run succeeds (`621-623`).  A
`KeyboardInterrupt` is not caught by the per-run `except Exception` at
`609-620`, and a process killed between the run-directory creation (`564-567`)
and `result.json` write leaves an unclassified attempt.  The CLI catches a
limited set of ordinary exceptions only (`tabpack/cli.py:129-135`).  Thus a
cancelled run has no structured cancelled result or finalization timestamp;
strict reporting sees a missing observation rather than a diagnosed failure.

**Minimal fix:** write an atomic progress/status record before each attempt,
catch user cancellation at the run boundary, emit a controlled `cancelled`
result and finalized manifest, and preserve failed attempts without
re-using their run IDs.  Make `report` distinguish running, cancelled,
failed, and missing records before calling strict aggregation.  Add tests for
exception and cancellation at model, test, checkpoint, and report stages.

### F4 — High: `report` trusts result JSON and does not verify artifacts

`report_comparison` loads the manifest and every `*/result.json`, then passes
the records to the in-memory aggregator (`tabpack/experiment.py:645-658`).
It writes the summary/table without checking that the manifest and each
record agree on protocol/comparison/config/data/source/environment hashes,
that the declared checkpoint exists, that its bytes match a digest, or that a
checkpoint reconstructs the selected snapshots (`659-712`).  The checkpoint
payload itself contains weights and selection metadata but no payload hash,
data/config/source identity, or explicit per-member lineage
(`456-473`).  `aggregate_results` is intentionally a pure summary helper;
it cannot supply these filesystem integrity checks (T53 note `150-153`).

**Minimal fix:** add a report-side schema/integrity validator before
aggregation: validate expected run IDs and matrix, compare all identity
fields to the manifest, require complete result/checkpoint files, hash and
verify each declared artifact, and verify selected snapshot/member/epoch
lineage.  Fail closed on missing, extra, stale, or mismatched artifacts.
Publish a secret-free manifest/provenance index with these hashes, following
T48's one-way hash rules, rather than treating aggregate metrics as sufficient
evidence.

T57 independently confirmed one concrete instance of this gap: replacing the
manifest `comparison_hash` with zeros was accepted and produced a report
(`docs/agents/T57.md:44-59`).

### F5 — High: checked-in measurements are not tied to the current source

The measurement checkpoint explicitly says the run happened before the first
local Git commit and has `source.local_commit: null`
(`docs/checkpoints.md:60-64`).  The checked-in report nevertheless presents
the three-seed measurements as the measured result
(`reports/churn-reduced/report.md:3-15`, `README.md:17-31`), while the local
runner is now being corrected for RNG routing, epoch IDs, determinism, and
configuration.  The ignored `runs/churn-reduced` artifacts are not present in
the checked-in workspace, so a reviewer cannot inspect the selected snapshots,
per-run manifest, checkpoint hashes, or execution source.  This does not show
that the numeric values are false; it shows that they are not currently
reproducible/auditable against the corrected implementation.

**Minimal fix:** after the reviewed source is committed, rerun all declared
method/seed observations, retain the execution commit and immutable source
inventory, publish the secret-free manifest/provenance and artifact hashes,
and regenerate `reports/churn-reduced/`.  Until then label the existing table
as pre-commit/RC evidence, not final release evidence.

### F6 — Medium: snapshot lineage is not fully represented in checkpoints

The positive part is sound: T51 documents that `PackedMLP.extract_member`
returns independent storage and preserves the caller RNG stream
(`docs/agents/T51.md:112-119`), and the runner keeps extracted current/prior
modules in separate dictionaries (`tabpack/experiment.py:398-422`).  The
remaining release issue is lineage: `_checkpoint_payload` stores each module's
architecture/state but not its member ID or source epoch; the only mapping is
an external ordered `selection.selected_snapshot_ids` list
(`456-473`).  Ordinary IDs use `epochs_completed` as the selected epoch even
when an earlier checkpoint won (`254-269`), and homogeneous IDs say `@best`
without an epoch (`323-330`).  T53 explicitly requires the caller to preserve
source-epoch state and candidate IDs (`docs/agents/T53.md:183-191`).

**Minimal fix:** make every serialized member entry carry the exact
`candidate_id`, `member_id`, `source_epoch`, and payload hash; use the actual
best epoch for ordinary/homogeneous records.  Add a test that mutates the
live/next model after selection and proves the frozen checkpoint's logits do
not change, then round-trips the selected IDs to payload entries.

### F7 — Medium: test-only-after-freeze is not persisted as release evidence

The execution order is favorable: training/validation selection returns first,
then test probabilities/metrics are computed (`tabpack/experiment.py:569-575`).
T57's synthetic integration test now spies on this order and passes, so no
leakage failure is claimed.  Production artifacts still contain no
selection-freeze or test-start/end timestamps, and the model and
`PreparedData` objects containing test data are passed through the whole
runner.  T50 requires chronology evidence (`docs/agents/T50.md:49-53`,
`129-139`), and T53 leaves freeze/test evaluation to the caller
(`docs/agents/T53.md:110-113`).

**Minimal fix:** retain T57's spy as a regression test and record
selection-freeze and test-start/end timestamps in the run artifact.  This is
an evidence/provenance gap, not a claimed observed leakage failure.

### F8 — Medium: source identity is not part of the comparison identity

`_run_identity` hashes config/data/environment and hard-codes all three method
names (`tabpack/experiment.py:504-519`), but does not include the local
implementation SHA, dirty/source inventory, or the actual `methods` argument.
The `comparison_hash` is computed before the manifest's source object is
assembled (`522-555`).  A subset-method run can therefore carry an identity
that says all methods were part of the comparison, and two source revisions
can share a comparison hash when their config/data/environment match.

**Minimal fix:** pass the validated unique method tuple into `_run_identity`
and include source SHA/dirty inventory, effective method rules, and the
algorithm/version constants in the hashed identity.  Keep upstream reference
SHA separate from local implementation identity as T48 requires
(`docs/agents/T48.md:28-35`, `62-72`).  Reject duplicate method names before
creating output.

### F9 — Low/Medium: report generation can overwrite an existing report

`report_comparison` creates the destination if needed and then replaces
`summary.json` atomically while writing CSV/Markdown directly
(`tabpack/experiment.py:659-712`); the CLI exposes no overwrite/attempt guard
(`tabpack/cli.py:122-125`).  A typo in `--output` can silently replace a prior
evidence directory, and an interruption can leave mixed-generation files.

**Minimal fix:** require an empty destination or explicit `--force`, stage all
report files in a fresh temporary directory, and atomically publish the
directory/index only after all validations and writes succeed.  Preserve the
input run directory and its identity in the output.

## Confirmed known integration issue from T51/T53

T53 says the execution layer must initialize from each member's
`streams["initialization"]` and route permutation/dropout draws through the
resolved streams (`docs/agents/T53.md:53-61`, `183-191`).  The current runner
does use named permutation generators in the ordinary/homogeneous/packed loops,
but packed initialization resets one global seed (`experiment.py:348-350`) and
model dropout uses global torch draws in `models.py:286-298`; ordinary dropout
also uses the global module RNG (`models.py:98-102`).  This confirms the
coordinator's already-listed RNG blocker.  T51's independent snapshot seam is
otherwise used correctly by the packed candidate path, subject to F6's
serialized lineage requirement.

## Claims and protocol audit

- No new paper-equivalence overclaim was found.  The report/README explicitly
  identify the local ROC-AUC/log-loss metrics and the official accuracy
  difference, and call the method reduced/optimistic.
- The implementation's packed loss, probability averaging, validation-only
  candidate selection, and final test ordering are consistent with the
  documented reduced protocol at the source lines cited above.  The runner
  does not use test labels for selection in the reviewed path.
- Timing claims need the F2 boundary correction; current `fit_wall_s` values
  should not be described as packing-only or complete workflow costs without
  clarifying the omitted construction time and fixed execution order.
- Source/data/config provenance and the absence of checked-in run artifacts
  are the principal release blockers.  Existing aggregate values are useful
  descriptive evidence, but should remain RC until a committed, corrected,
  independently verifiable rerun exists.
