## Resolved contracts

`tabpack.core` exports `SEED_ALGORITHM = "sha256-named-v1"` and
`SAMPLING_ALGORITHM = "sha256-named-v1/python-random-mt19937-v1"`. `named_seed`
uses type-tagged, length-delimited SHA-256 paths and a 63-bit big-endian prefix;
it does not use Python `hash()`, additive member seeds or mutable global RNG.
Each member gets independent local field RNGs for architecture sampling and
named training roots for `initialization`, `permutation`, and `dropout`.
Sampling is prefix-stable, so one member versus four preserves member 0. The
current sampler redraws heterogeneous member settings for each root run seed;
that is the selected optimistic policy. Homogeneous values repeat but stream
IDs remain distinct.

Current tests verify same-seed/global-RNG isolation, prefix stability, field
stream isolation, distinct member stream IDs, `PYTHONHASHSEED` subprocess
stability and the independent log-uniform oracle. T53 reports these in its
**140 passed** focused run. `MemberSpec` serializes resolved values and streams,
so rehydration does not resample.

## Execution-layer requirements

The core only supplies stream identities; actual trainer integration must route
all random draws through them:

1. Initialization: member-local deterministic CPU/device policy, with active
   shapes initialized before copying into packed storage. A neighbor's padding
   must not consume the member's logical stream.
2. Permutations: derive a per-member/per-epoch stream and draw each `randperm`
   independently. Index both features and labels. Use `num_workers=0` on Windows
   unless a worker seed initializer/generator is explicitly captured.
3. Dropout: current `PackedMLP` uses member-aware native masks and accepts an
   explicit per-layer `[M,B,Hmax]` boolean `dropout_masks` seam for exact tests.
   T51 says native dropout trajectories across pack sizes/layouts are not
   promised equal; controlled-mask equivalence is the valid oracle.
4. Checkpoint/resume: capture generator states or materialized next permutations
   at epoch boundaries before generating them, together with Python/NumPy/Torch
   state as applicable. Restore after model construction and before iterator or
   evaluation creation; never redraw member configs or refit preprocessing.
5. CUDA: record device, deterministic algorithms, cuDNN benchmark and TF32
   policy. Exact CPU/CUDA bitwise identity is not promised.

The packed model's `from_members` and `extract_member` use `torch.random.fork_rng`
with CPU-only device lists, avoiding accidental CUDA RNG consumption during
snapshot/module construction. That is a current implementation observation,
not proof that the future trainer's initialization path is isolated.
