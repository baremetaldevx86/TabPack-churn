# T13 — Deterministic configuration and member-sampling design

## Assignment and scope

This note reviews the reduced Churn experiment's configuration and member
sampling contract. It is design guidance for the coordinator and future
implementation owner; it deliberately does not add source code, install
dependencies, execute training, or run long experiments.

The reduced protocol in `swarm.md` has three run seeds (`0, 1, 2`), four base
members, a maximum selected ensemble size of four, float32, and the stated
baseline and heterogeneous search spaces. The sampling API should make every
effective choice explicit, serializable, and independently reproducible.

## Recommended public API boundary

Use three conceptual operations, with names left to the implementation owner:

1. `load_config(source) -> ExperimentConfig`: parse JSON/TOML/CLI input into a
   typed configuration, rejecting unknown keys and malformed values.
2. `resolve_config(config, *, run_seed) -> ResolvedRunConfig`: expand all
   defaults, choose the sampling seed according to an explicit policy, and
   materialize the ordered member records. It must not mutate the input.
3. `sample_members(resolved_sampling, *, sampling_seed) -> list[MemberSpec]`:
   produce a fresh ordered list of JSON-safe member specifications. The model
   and training code consume this list; they must not sample again.

The resolved object should also expose named stream identities (or their
integer seeds) to model initialization, permutations, and dropout. Returning
opaque live RNG objects from a config API would make serialization and resume
ambiguous; generators belong to the execution layer and are reconstructed from
the recorded stream descriptors.

## Input configuration shape

The following is a proposed JSON-safe shape. It is an API/data-structure
sketch, not a required spelling:

```json
{
  "schema_version": 1,
  "method": "packed_heterogeneous_ensemble",
  "run_seed": 0,
  "sampling": {
    "algorithm": "seedsequence-pcg64-v1",
    "scope": "per_run",
    "n_members": 4,
    "member_ids": [0, 1, 2, 3],
    "discrete": {
      "depth": [1, 2, 3],
      "width": [32, 64, 96],
      "dropout": [0.0, 0.1, 0.2]
    },
    "log_uniform": {
      "learning_rate": [0.0003, 0.003],
      "weight_decay": [0.000001, 0.001]
    }
  },
  "training": {
    "batch_size": 256,
    "max_epochs": 100,
    "patience": 16,
    "dtype": "float32"
  }
}
```

The homogeneous path should use the same `MemberSpec` representation but set
all member model/optimizer values to the resolved baseline (`depth=2`,
`width=64`, `dropout=0.1`, `learning_rate=0.001`, `weight_decay=0.0001`).
Homogeneous sampling has no hyperparameter draw, but it still creates four
distinct member stream identities and four independent parameter/training
states. Equal configs must never imply shared parameters or a shared RNG.

Every resolved run should contain at least:

```text
ResolvedRunConfig {
  schema_version: positive integer
  method: known enum
  run_seed: nonnegative integer
  sampling_seed: nonnegative integer
  sampling_scope: "per_run" | "shared_experiment"
  sampling_algorithm: stable algorithm/version identifier
  member_count: positive integer
  members: ordered list[MemberSpec]
  protocol: fully resolved budgets and numerical policy
  config_sha256: hash of canonical resolved content (optional until writer)
}

MemberSpec {
  member_id: stable string such as "member-0000"
  member_index: nonnegative integer
  model: resolved depth/width/dropout/etc.
  optimizer: resolved learning_rate/weight_decay/etc.
  stream_ids: named stream paths or derived integer seeds
  sampling_draws: optional auditable categorical indices and log-uniform u's
}
```

Use one stable member-ID convention throughout checkpoints, predictions,
selection, and CSV exports. A numeric `member_index` is useful for tensor
packing, but the serialized string ID protects identity when records are
sorted or displayed. Reordering the input dictionary must not reorder members;
the explicit `member_ids`/index order is authoritative.

## Deterministic sampling contract

### Sampling scope must be explicit

Support both policies, but do not infer one from an omitted field:

- `per_run`: derive `sampling_seed` from the experiment master seed and the
  run seed, so each seed is an independent draw of the heterogeneous pool.
- `shared_experiment`: derive one experiment-level `sampling_seed`, then reuse
  the same ordered member hyperparameters for all run seeds; initialization,
  permutations, and dropout still use run-specific member streams.

For the reduced study, the coordinator/T40 should select and document one
policy before measurements. Recommend `per_run` as the provisional policy,
consistent with T27's per-seed sampling description. `per_run` exposes sampling variability as part of
each replicate; `shared_experiment` isolates initialization/training-seed
variability. In either case, the result artifact must record the policy,
master/sampling/run seeds, and fully realized members. Never silently resample
when loading a resolved configuration or checkpoint.

### Domain-separated stream derivation

Do not use Python's process-randomized `hash()`, a mutable global RNG, or
`root_seed + member_index`. Derive each stream from a versioned, canonical
path containing the experiment seed and stable IDs, for example:

```text
stream_path = [
  "tabpack-reduced-rng-v1",
  experiment_seed,
  sampling_scope,
  run_seed_or_shared_marker,
  method,
  member_id,
  purpose,
  field_or_epoch_or_batch
]
```

The implementation may use NumPy `SeedSequence` spawning or a domain-separated
SHA-256 digest followed by the declared generator family. The choice must be
fixed in `sampling_algorithm`; record generator family/version and integer
seed width. Child paths must be independent of call order and execution
order. Never share one mutable generator between architecture sampling,
initialization, data permutations, and dropout.

The shared marker is allowed only for hyperparameter sampling; initialization,
permutation, and dropout paths always include the actual run seed. Do not put
the whole config hash, member count, execution position, or current packed
shape into the stream key: those would destroy prefix/order independence.
If using `SeedSequence`, assign stable numeric domain/field IDs or derive
entropy from a canonical path digest; strings cannot be passed as entropy.
Calling `spawn()` opportunistically in execution order is insufficient.

Recommended purpose names are:

- `hyperparameter/depth`, `hyperparameter/width`,
  `hyperparameter/dropout`, `hyperparameter/learning_rate`, and
  `hyperparameter/weight_decay`;
- `initialization`;
- `permutation/epoch-<e>` (or a recorded generator state at an epoch
  boundary);
- `dropout/layer-<l>/epoch-<e>/batch-<b>` when the backend needs explicit
  masks.

Named field streams make adding a future unrelated hyperparameter harmless to
the existing fields. Member-local streams make sampling count prefix-stable:
sampling one member and sampling four members with the same resolved protocol
must produce the same `member-0000` record. Training execution order and the
order in which seeds are launched must not change any member record.

For packed dropout, a single vectorized operation may consume a contiguous
member-shaped random tensor, but its stream must be member-aware and must not
create one mask shared across members. If the backend cannot supply separate
generators to dropout, pre-draw masks from member/layer/batch-specific streams
or use a documented stateless seed path. T35's epoch-boundary checkpoint must
capture generator state or the next exact permutations/masks needed for
continuation.

Initialize each member's active parameter shapes from its own initialization
stream, then copy into packed storage. A larger neighbor's padding must not
consume that member's random draws. For permutations, use a member/epoch-local
CPU generator to draw `randperm(n_train)` and move the indices to the target
device. Slice the permutation into batches without dropping the tail. Ordinary
dropout APIs may consume device-global state even if a generator was created
elsewhere; the forward implementation must actually use the intended stream.
Deterministic sampling does not imply bitwise equal CPU/CUDA training.

### Homogeneous members

For each member index `i`:

1. Copy the immutable resolved baseline values into a new `MemberSpec`.
2. Derive `initialization`, `permutation`, and `dropout` stream paths using
   `member_id=i`; do not use the same generator merely because configs match.
3. Preserve member order and IDs in the resolved artifact.

There is no requirement that random permutations never coincide by chance. The
requirement is that the logical streams are distinct, deterministic, and
unaffected by another member's draws or execution order.

### Heterogeneous members

For each member index `i`, draw independently from the declared spaces using
the member's named hyperparameter streams:

- discrete choices are uniform index draws from the declared list;
- log-uniform `x in [lo, hi]` uses
  `exp(log(lo) + u * (log(hi) - log(lo)))`, with `u` in `[0, 1)`;
- `lo == hi > 0` is legal and returns exactly `lo`, avoiding a zero-width
  numerical path;
- duplicate discrete choices should be rejected rather than silently giving
  an option extra probability weight;
- sampled values remain finite and within the declared closed bounds (the
  upper endpoint is normally approached, not emitted, by `[0,1)` draws).

Record either the auditable draw values/indices or enough generator metadata to
replay the exact sample. The fully resolved value is mandatory even if the
draw is retained. Rehydrating `MemberSpec` must not call the sampler.

## Validation and serialization requirements

Validate before any random draw or model allocation:

- positive integer counts; reject booleans, fractional values, numeric
  strings, empty member lists, and duplicate run seeds;
- recommend seed domain `0 <= seed < 2**63`, with boolean seeds rejected;
  record any seed-width conversion in the derivation version, never silently
  truncate a user-provided seed;
- finite dropout values in `[0, 1)`;
- finite positive learning rates and finite nonnegative weight decay;
- exactly two finite positive endpoints for each log-uniform range, with
  `low <= high`;
- nonempty homogeneous/heterogeneous discrete choice lists with valid typed
  values and no duplicate choices;
- supported method, dtype, algorithm, and sampling-scope enums;
- `member_ids` unique and in a stable explicit order;
- no unknown keys or malformed nested structures.

Require positive patience; patience greater than max epochs is legal. Do not
enforce `selection_limit <= member_count`: the current-plus-retained snapshot
pool can contain more candidates than current base members (T26 C14).

The typed validator should reject NaN/Infinity before comparisons. CLI string
conversion belongs at the parser boundary; the typed API should not silently
coerce strings or booleans. Errors should include a field path and fail before
creating run artifacts.

Serialize only JSON-safe primitives: lists rather than sets/tuples, strings,
integers, booleans, finite numbers, and explicit nulls where allowed. Do not
serialize live RNG objects, function references, absolute paths, secrets, or
host-specific values in the resolved config. Canonical JSON should follow the
provenance convention in T48 (`sort_keys`, compact separators, UTF-8,
`allow_nan=False`), with a schema and sampling algorithm version. Hash the
resolved ordered records, not merely the user's short input file. Floating
values should be retained unrounded; presentation can round later.

## Tests and status

No implementation or test suite exists in the repository at this review, and
no tests, dependency installation, model construction, or training were run.
The following fast tests should be implemented after the API is frozen:

1. Same resolved config/seed twice, with unrelated global RNG draws between
   calls, yields byte-identical ordered members and stream descriptors.
2. Reordered config dictionary keys and different `PYTHONHASHSEED` values do
   not change output; changing an explicitly ordered choice list may change
   output and must be documented.
3. Sampling one versus four members preserves the first member exactly.
4. Forward, reverse, and isolated execution of run seeds preserves each seed's
   resolved records.
5. Homogeneous records have identical model/optimizer values but unique stream
   identities; heterogeneous records satisfy spaces and bounds, including
   singleton choices and equal positive log endpoints.
6. Changing hyperparameter stream consumption does not change initialization,
   permutation, or dropout stream descriptors; no purpose uses a global RNG.
7. Invalid configurations fail before the first random draw, and serialized
   resolved configs round-trip without resampling or input mutation.
8. Independent expected values for at least one categorical index and one
   log-uniform transformation verify the sampler rather than calling the same
   production helper as the oracle.

Exact cross-platform floating-point golden values should use a documented
tolerance for log/exp; integer member IDs, stream derivation records, and
categorical choices should be exact. Do not assert that every random vector or
permutation differs, because coincidence is possible.
