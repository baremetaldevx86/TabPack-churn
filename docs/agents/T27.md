# T27 — Architecture documentation

## Assignment and scope

This note supplies the architecture documentation for the self-contained Churn
experiment. The experiment compares three deliberately small systems:

1. one ordinary MLP;
2. a homogeneous ensemble of independently trained MLPs; and
3. a reduced heterogeneous, packed **TabPack-style** ensemble.

The third label is intentional. This repository is an independently authored,
self-contained experiment. It is not the official TabPack implementation, an
official release, or a reproduction of the paper's full protocol. The paper
(v1, `https://arxiv.org/html/2607.05380v1`) and the official repository at
commit `05a89e21b955f12de84889d662e15ca534019aaa` are reference material only;
their code is not imported or executed here. This document describes the
intended local architecture from the coordination ledger, not a verified
implementation inventory or an independent audit of the official sources.

## System boundary

The four architectural stages are data preparation, model training,
validation-only selection, and frozen test reporting. In prose, the diagram
branches a single train-fitted feature schema into three model paths; only the
packed path maintains the online heterogeneous snapshot pool. Every path
freezes its validation-selected state before producing its test report:

```text
canonical Churn train/validation/test split
                |
                v
train-fitted preprocessing (numeric + categorical)
                |
                v
seed/config member factory  ---> ordinary MLP
                |              independent homogeneous MLP members
                `------------> packed heterogeneous member pool
                                      |
                                      v
                         validation-only greedy selection
                                      |
                                      v
                         frozen probability-average ensemble
                                      |
                                      v
                              one final test report
```

Preprocessing is fitted on the training split only and then applied without
refitting to validation and test. Numeric columns use median imputation and a
quantile-normal transform; categorical columns use most-frequent imputation
and one-hot encoding with unknown categories ignored. The model architecture
must not have access to test labels, and test evaluation occurs only after
checkpoint and member selection are frozen.

The provisional reduced budget is three seeds (`0, 1, 2`), four base members,
maximum selected ensemble size four, at most 100 epochs, patience 16, batch
size 256, and float32. Baseline MLPs use depth 2, width 64, dropout 0.1,
AdamW learning rate 0.001, and weight decay 0.0001. Heterogeneous members
draw from depths `[1, 2, 3]`, widths `[32, 64, 96]`, dropout `[0, 0.1, 0.2]`,
log-uniform learning rate `[0.0003, 0.003]`, and log-uniform weight decay
`[0.000001, 0.001]`. These are exposed experiment settings, not claims about
the official paper configuration.

## Three model paths

### Ordinary MLP

The ordinary baseline consumes a batch `X` and produces one binary logit per
sample. Its hidden layers are conventional dense layers with the configured
width, activation, and dropout. Its parameter count and optimizer state are
those of one model.

### Independent homogeneous ensemble

The control ensemble contains `M` separate copies of the same architecture.
Each copy has independent parameter storage, initialization, dropout masks,
optimizer state, and training permutation. They may be trained in one loop or
as separate modules, but they must be mathematically equivalent to separate
models. At inference, each member emits a probability and the ensemble emits
their arithmetic mean. This control measures the effect of homogeneous
ensembling relative to one MLP. A heterogeneous packed comparison also changes
member configurations and selection; it cannot alone isolate a packing effect.

### Reduced heterogeneous packed ensemble

The packed path keeps the member axis explicit and evaluates the member pool
as a single vectorized computation. Members may differ in depth, width,
dropout, learning rate, and weight decay. A concrete implementation can use
shape-compatible layer groups or padded/masked slots for heterogeneous layers;
the representation chosen by the implementation must preserve the semantics
below. Padding is an execution convenience, not a member parameter or a source
of cross-member connections.

Conceptually, every member remains an ordinary MLP. Packing changes execution
layout and optimizer traversal, not the model family or the independence of
the members. A member with fewer layers must not receive computation from a
deeper member merely because both occupy one packed tensor.

## Packed tensor contract

The first tensor dimension is the member dimension. Use `M` for members, `B`
for batch size, `F` for input features, and `H_m` for member-specific hidden
width. In prose, the tensor diagram replicates the evaluation inputs along the
member axis, transforms each member slice independently, and reduces that axis
only when averaging probabilities. The conceptual dataflow is:

```text
X                         [B, F]
  broadcast for evaluation
X_pack                    [M, B, F]
  member-specific dense + activation/dropout
hidden member m            [B, H_m]     (packed padded form: [M, B, H_max])
  member-specific output head
logits_pack               [M, B, 1]
probabilities_pack        [M, B]
mean over member axis      [B]
```

The notation `[M, B, ...]` is a semantic contract even if a backend groups
compatible layers or flattens dimensions internally. In particular:

- `M` is not a feature, channel, or batch dimension. Reducing or averaging
  over it is an explicit ensemble operation.
- Evaluation input broadcasting is allowed because all members see the same
  ordered samples. During training, independent member permutations instead
  produce `X_pack[m,b] = X[permutation_m[b]]` and corresponding labels
  `y_pack[m,b] = y[permutation_m[b]]`. Never broadcast one member's labels over
  independently shuffled inputs.
- Every member owns its own weights and biases. There are no cross-member
  linear terms and no overlapping trainable elements. Disjoint slices of one
  packed allocation are valid; independence does not require separate buffers.
- Dropout and other stochastic operations are member-independent; a packed
  mask has a member axis (for example `[M, B, H]`) rather than one mask shared
  by all members.
- Heterogeneous widths and depths are represented by member-specific active
  regions. In padded layouts, inactive slots are masked and cannot contribute
  to an active member's output or gradient.
- The packed output is a collection of member predictions, not a single
  prediction produced by a wider shared network.

For a binary member logit `z_m,b` and its aligned training label `y_m,b`, member
loss is

```text
L_m = (1 / B) * sum_b BCEWithLogits(z_m,b, y_m,b)
L_pack = sum_m L_m
```

The member losses are averaged over samples and **summed over members**. They
are not silently averaged over `M`, and the training objective is not the loss
of the probability-averaged ensemble. This preserves the agreed packed
optimizer semantics and makes any member-count-dependent gradient scaling
explicit. For distinct members `m` and `n`, `d L_m / d theta_n = 0`:
vectorization must not introduce a gradient path between their parameters.
At inference, probability averaging is separate and predictions share the same
sample order:

```text
p_m,b = sigmoid(z_m,b)
p_ensemble,b = (1 / |S|) * sum_{m in S} p_m,b
```

where `S` is the selected snapshot/member set. A head may expose logits as
`[M,B]` instead of `[M,B,1]`; the member-first meaning remains unchanged.
Averaging logits instead would
be a different aggregation rule and should not be substituted without an
explicit protocol change.

## Training and selection semantics

Each seed gets independent member sampling and random state. A packed batch
updates all active members while retaining independent parameters, stochastic
masks, and optimizer moments. A packed AdamW implementation must be equivalent
to applying AdamW separately to every member, including per-member learning
rates and weight decay where configured. The packed layout must not make
members share optimizer moments.

The online candidate pool consists of current-epoch member checkpoints plus
previously selected checkpoint snapshots. Snapshot identity therefore includes
the member identity and epoch; two snapshots may share a member ID while
representing different epochs. Greedy selection is without replacement and
accepts a candidate only when validation ROC-AUC strictly improves. Validation
ROC-AUC chooses checkpoints and candidates; the test split is untouched until
the final selected set is frozen.

This selection stage is an ensemble consumer of the architecture, not a fourth
model type. The same probability-averaging rule is used for ordinary ensemble
members and packed members so that the comparison is about construction and
execution rather than an aggregation mismatch.

## Official versus experimental semantics

The following are deliberate boundaries for documentation and result naming:

| Topic | This experiment | Attribution / claim boundary |
| --- | --- | --- |
| Source | Independently authored local implementation | Reference repository/paper only |
| Scope | Churn-only reduced experiment | Broader paper/repository scope |
| Members | Four provisional base members, three seeds | Do not infer official count or schedule |
| Features | No periodic feature embeddings | Not implemented in this reduction |
| Optimization | AdamW | Muon and other official choices are not claimed |
| Search | Exposed reduced heterogeneous draws; no tuning | No claim of official search protocol |
| Pruning | No base pruning | Not represented in this reduction |
| Selection | Validation-only greedy snapshots, strictly improving | Use as the local protocol definition |
| Results | Local measurements only | Never label as paper-reported scores |

Use “packed TabPack-style”, “reduced experiment”, or equivalent wording in
tables, filenames, and prose. The local evaluation is the provisional
**reduced TabPack-style optimistic evaluation**, not paper-equivalent scoring.
Do not describe the result as “TabPack” without
the qualifier, and do not imply that a packed tensor alone reproduces every
official feature or claim.

## Resource interpretation

Packing is an execution representation, not automatic parameter compression.
The logical parameter count is the sum of each member's parameters, and
optimizer state likewise belongs to each member. Padded heterogeneous storage
may add temporary capacity for `H_max` or the deepest layer; report the actual
logical/member counts and, where measured, packed storage separately. Isolating
the runtime or memory effect of packing requires a matched looped-versus-packed
comparison using the same member configurations, batch streams, and training
budget. The three scientific model paths alone do not provide that ablation.

## Tests and current status

No implementation files or test suite were present when this note was drafted;
therefore no tests were run and no training was run. The architecture should be
accepted only after the implementation-level checks owned by the related tasks
are available, especially:

- packed forward output versus independently evaluated members;
- packed AdamW updates versus independent AdamW updates;
- member-axis loss reduction (`mean` over samples, `sum` over members);
- no overlapping member parameters, cross-member optimizer moments, or
  unintentionally broadcast stochastic mask;
- heterogeneous depth/width masking and inactive-slot gradient behavior; and
- probability averaging and validation-only greedy selection.

The absence of test results here is a status report, not evidence of passing
behavior.
