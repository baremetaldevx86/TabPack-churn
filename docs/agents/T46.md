## 1. Parameter accounting: capacity versus storage

Let `F` be the **actual train-fitted transformed feature count**, `L >= 1` the
number of hidden Linear–ReLU–Dropout blocks, and `H` their constant width.
There is a separate biased one-logit binary output head. With biases in every
linear layer and no trainable embeddings or normalizations:

```text
P(F,L,H) = (F*H + H) + (L-1)*(H*H + H) + (H + 1)
         = F*H + (L-1)*H^2 + (L+1)*H + 1
```

ReLU, dropout, sigmoid, and probability averaging add no trainable parameters.
Do not use raw column count or count one-hot features as trainable embeddings.

| Method | Logical training parameters | Stored model parameter elements |
| --- | --- | --- |
| Ordinary MLP, `L=2,H=64` | `64*F + 4,289` | Same |
| Four homogeneous independent MLPs | `256*F + 17,156` | Same if all four weights are resident |
| Heterogeneous members `(L_m,H_m)` | `sum_m P(F,L_m,H_m)` | Read actual tensor `numel`; layout dependent |
| Full rectangular padded pack | Same logical sum | `M*P(F,L_cap,H_cap)` |

Here `L_cap >= max(L_m)` and `H_cap >= max(H_m)` are **allocated** capacities.
The official sampler can allocate its search-range upper bound even if that
bound was not drawn. Use recorded tensor shapes, not just sampled maxima.
Grouped/ragged layouts can have smaller storage; the rectangular formula must
not be applied to them without checking their tensor inventory.

For four members within the reduced range, the logical count is bounded by
`128*F + 260` (all depth 1/width 32) and `384*F + 75,268` (all depth 3/width 96).
With capacity `(3,96)`, the rectangular packed stored count is the latter even
for smaller members. Record `padding_ratio = stored/logical` and both counts.
`sum(p.numel() for p in model.parameters())` counts padded storage, including
masked slots. It is not the logical capacity and is not reduced by zero-valued
weights or zero gradients. Masks and metadata are buffers, counted separately.

Equal member counts do not imply equal capacity. If width and depth are sampled
independently and uniformly from their three listed choices, expected member
capacity is `64*F + 14,915/3`, versus `64*F + 4,289` for the baseline. The
difference is `2,048/3` parameters per member because width enters quadratically.
Record the actual sampled architectures/counts per seed, not this expectation.
The primary comparison is a method comparison, not a parameter-matched ablation.

## 2. Training memory and final-predictor memory

For dense float32 AdamW with float32 moments, a basic live training inventory is:

```text
weights                 4 * P_stored bytes
first + second moments  8 * P_stored bytes, after lazy initialization
live gradients          4 * P_stored bytes
core total             16 * P_stored bytes
```

This is a component estimate, **not peak memory**. If gradients are set to
`None`, that phase omits their storage. Moment initialization, absent whole
layers, optimizer implementation, and differing state dtypes require counting
actual state tensors. Dense masks do not make gradients or moments sparse.
Additional masks, counters, and hyperparameter vectors must also be counted.
The illustrative padded pack's core is only 1.24225 MiB, excluding everything
below; this is not a prediction of process or GPU peak.

Peak allocation also includes:

- **Activations/autograd/dropout:** one float32 hidden tensor `[M,B,H_cap]`
  costs `4*M*B*H_cap` bytes. For `(4,256,96)`, that is 393,216 bytes
  (0.375 MiB) per such tensor. Several saved and temporary tensors can coexist;
  exact peak depends on depth indexing, masking, dropout, and backward.
- **Data and batching:** dense float32 transformed data costs approximately
  `4*N*F` bytes per resident copy, plus labels/raw data/transform temporaries.
  Independently gathered training inputs `[M,B,F]` are materialized in normal
  advanced indexing. A shared inference `expand` view is not `M` physical input
  copies. Int64 epoch permutation indices `[M,N_train]` cost `8*M*N_train` bytes;
  sort-based generators additionally allocate random keys and sorting workspace.
- **Online snapshots:** count immutable inference weights once per retained
  snapshot, plus temporary copies during selection/checkpoint writing. Compact
  snapshots cost `4*sum P_snapshot` bytes; padded member snapshots are larger.
  The live candidate set is at most `M+K_previous <= 8` in this reduction, but
  separately retained historical-best selections can increase resident storage.
  Never duplicate the full packed optimizer inside every selected snapshot.
- **Validation predictions:** one float32 cache `[C,N_val]` costs
  `4*C*N_val` bytes. Concatenation, historical caches, CPU/GPU copies, and greedy
  temporary ensemble vectors add storage. Count only actual copies, with dtype.
- **Runtime overhead:** optimizer temporaries, BLAS/workspace allocations,
  allocator caching, Python/runtime, worker processes, and serialization buffers.

A homogeneous serial runner can train with one optimizer/activation graph at a
time and retain completed weights on CPU. A runner retaining all four optimizers
has a different peak. Likewise, sequential member backward can free graphs
earlier than summing all member losses before one backward. Record the actual
residency/backward policy instead of asserting every ensemble uses four times
the single model's peak.

For deployment, count the **selected snapshots**, not the training pool. Two
epochs of the same member represent two predictors and two weight sets unless
identical storage is deliberately deduplicated. Report compact logical final
parameters and actual deployed parameters/bytes separately. If inference runs
all training members and selects predictions afterward, its measured work and
resident storage are those of the full pack, not the smaller selected set.

### Measurement contract

Use T37's fresh process per method/seed and synchronized CUDA phase boundaries.
Record `torch.cuda.max_memory_allocated()` and `max_memory_reserved()` in bytes
with an explicit peak-reset boundary; record setup, fit/selection, and frozen
inference peaks independently if possible. Resetting peak statistics does not
free existing allocations, so retain the phase-start allocated/reserved values.
PyTorch allocator figures exclude some driver/context/other-process memory and
are not interchangeable with `nvidia-smi` device usage. For CPU, use process RSS
with the sampler/API and interval recorded; `tracemalloc` misses native tensor
memory. Missing observations are null with reasons, not zero. Disk checkpoint
file sizes are a separate resource, not RAM or VRAM.

The paper's Appendix A.6 Table 4 averages 17 datasets, includes embeddings, and
reports TabPack-dagger peaks of 0.6 GB at four members and 5.8 GB at 64. These
are neither Churn-only values nor estimates for this reduced no-embedding run.
T19 preflight should distinguish calculated components, uncertain overhead, and
actual observations; a small weight estimate alone cannot certify a fit.

## 3. Batch size, epochs, and work counters

`B=256` means **256 examples per member per optimizer update**, not 256 divided
among the ensemble. The full pack consumes up to `M*B=1,024` example–member
pairs. This is not a single model trained at effective batch size 1,024, nor
necessarily 1,024 distinct dataset rows. Independently permuted member batches
can overlap. Keep the same per-member batch size for the homogeneous control.

With `N` train examples, no dropped tail, no pruning, and `S=ceil(N/B)`:

| Quantity per epoch | Single MLP | Four-member homogeneous | Four-member packed |
| --- | ---: | ---: | ---: |
| Examples processed by each member | `N` | `N` | `N` |
| Example–member pairs processed | `N` | `4*N` | `4*N` |
| Member optimizer updates | `S` | `4*S` | `4*S` |
| Packed optimizer calls | N/A | Depends on runner | `S` |

The last member batch has its actual remaining size, which also normalizes its
loss. Training loss is sample-mean within each member, then member-sum; inference
probability averaging does not change training batch semantics.
At 100 full epochs, the single model sees `100*N` pairs and each ensemble
`400*N`; actual early stopping changes these totals. Count all trained members,
including ones absent from the final selection. Report completed epochs,
per-member updates/examples, total example–member pairs, and validation/selection
calls. Optimizer call counts alone would misleadingly equate one packed update
with one single-member update.

## 4. Compute accounting and interpretation

Define one multiply–accumulate as one MAC; quote FLOPs as approximately `2*MAC`
only with that convention stated. Ignoring biases and elementwise operations,
the active forward MAC count per example for one member is:

```text
A(F,L,H) = F*H + (L-1)*H^2 + H
logical ensemble forward MACs per shared example = sum_m A(F,L_m,H_m)
logical training forward MACs per full packed step = B * sum_m A(...)
```

Actual padded matrix work differs. With maximum-width dense layers and
`A_l = count(members with L_m >= l)`:

```text
depth-indexed forward MACs/step:
    B * [M*F*H_cap + sum_(l=2..L_cap) A_l*H_cap^2 + M*H_cap]

full compute-and-select forward MACs/step:
    B * M * [F*H_cap + (L_cap-1)*H_cap^2 + H_cap]
```

The official implementation skips absent depths using active-member indices,
but still stores rectangular per-layer tensors and performs padded width work.
A local `where` after computing every member's layer preserves semantics but
does not skip that matrix multiplication. Width masks applied after matmul also
do not remove padded MACs. Grouped layouts need sums of their actual shapes.

For the illustrative members above and batch 256: logical forward work is
7,929,856 MACs/step; depth-indexed padded work is 11,108,352; full padded work is
20,545,536. These are analytical counts, not profiler measurements or timings.
Training backward adds roughly two matrix products per linear layer when both
input/weight gradients are needed; the first layer often needs no input
gradient. Hence “training = three times forward” is only an approximation.
AdamW, masks, dropout, gathers/scatters, losses, validation, and greedy ROC-AUC
sorting add work and must not be hidden behind a purported exact FLOP total.

Packing primarily changes kernel launch overhead and hardware utilization. It
does not eliminate independent-member arithmetic, and padding may increase it.
Wall-clock speedup can coexist with greater MACs or memory. Keep total fit wall
time (training plus validation/selection, as T20/T37 specify) authoritative;
label model-forward MAC estimates separately. Inference throughput is complete
ensemble predictions per second (`N_test/time`), not member predictions per
second (`K*N_test/time`).

Homogeneous versus heterogeneous timings also vary in architecture, stopping,
and selection work. Those three methods alone cannot isolate a speedup caused
solely by packing. Such a claim would require a same-member/same-update
independent-versus-packed comparison; the existing short equivalence oracle
can establish correctness but not a representative training speedup.
