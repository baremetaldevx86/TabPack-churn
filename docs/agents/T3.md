## Findings

### Greedy algorithm and ties

The official `greedy_ensemble` defaults to `init_top_k=1`. It initializes with
the candidate having the maximum individual `score_fn` on validation. At each
subsequent step it forms the mean prediction of the current ensemble and each
not-yet-selected candidate, scores all resulting ensembles, and chooses the
maximum. The default is `with_replacement=False`, so the unit of uniqueness is a
candidate row/snapshot, not a base-model ID.

The implementation has two strict-improvement gates:

1. Within one greedy rebuild, if the best candidate's selection score is `<=`
   the current ensemble selection score, it stops; an equal-scoring candidate is
   not added. This is the code equivalent of the paper's “no further
   improvement” rule.
2. `OnlineEnsemble.update` replaces the previous epoch's ensemble only if the
   rebuilt ensemble's validation score is strictly `>` the stored score. An
   equal score leaves the previous ensemble unchanged and consumes patience.

For exact ties among candidate ensemble scores, the official code first keeps
all candidates at the maximum score, then selects the one with the best
individual score (`prediction_scores`). If that is still tied, `torch.argmax`
selects the first candidate in the existing pool order. Initialization likewise
uses the first maximum for `init_top_k=1`. Therefore a reduced implementation
should preserve a deterministic pool order and record it; it should not silently
deduplicate equal-member-ID snapshots. The official code has no tolerance-based
tie rule: comparisons are exact floating-point `>`/`<=` comparisons.

The default Churn configuration supplies neither `selection_score_fn` nor
`algorithm_score_fn="loss"`; alternative multi-score branches are outside the
reduced contract. The final returned indices are in ascending pool-index order
(from the selected mask), not necessarily greedy addition order. Persist greedy
trace order separately if it is useful for debugging.

Paper §3.6 defines patience `p` as stopping after **p+1** consecutive
non-improving epochs. The code agrees: remaining patience starts at `p`, decreases
for ties/regressions, and is running while `>=0`. Thus official ensemble patience
32 permits 33 non-improving epochs; reduced patience 16 would mean 17 under this
convention. If the coordinator chooses the usual stop-at-16 interpretation,
record that difference explicitly.

### Online candidate and checkpoint semantics

In `OnlineEnsemble._prepare_pool`, official `update_type="latest"` contributes
the latest validation predictions of every currently running base member. A
base model that has finished/been removed contributes its saved *best*
validation checkpoint (`FinalStatePack`); this is separate from the latest
running state. `update_type="best"` instead contributes each running member's
best checkpoint, while `update_type="final"` only uses finished members.

The pinned Churn config uses `update_type="latest"`,
`include_current_ensemble_in_pool=true`, and `max_ensemble_size=32`. Thus each
epoch's pool contains the previous online ensemble snapshots followed by
finished snapshots (if any) and current running latest snapshots; the previous
ensemble is prepended by `_prepare_pool` in the actual code. The previous
ensemble is itself a list of candidate snapshots, so the same `member_id` can
appear at multiple source epochs. Greedy selection without replacement prevents
selecting one candidate row twice during a rebuild, but does not prevent
selecting two different snapshots from the same member.

The pool is not an archive of every historical epoch. Only retained ensemble
snapshots, accumulated finished members' best snapshots, and current running
states survive into the next rebuild. Including the old members does not prove
the new greedy result will equal or beat the old ensemble; changing the greedy
path can lose its old combination. The outer strict-improvement gate is what
preserves the best accepted ensemble.

There is no pool deduplication in the pinned code. Consequently an identical
`(member_id, step)` can occur both in the old ensemble and finished-member pool
and can be selected twice as separate rows. This occurs in the published plain
Churn main report: IDs `[4,50,22,4,40,53]` with steps
`[225,225,125,225,775,775]` include `(4,225)` twice. Treat this as an upstream
implementation detail distinct from the paper's same-member/different-epoch
description. In a no-pruning reduced run with strictly increasing epochs, the
current and retained snapshots normally have distinct identities; if exact
duplicates can occur, choose and document a deduplication policy rather than
accidentally introducing implicit weights.

For this reduced protocol there is no base pruning, so the practical pool is:

```text
previous_selected_snapshots + current_epoch_latest(member 0..M-1)
```

Each snapshot should carry at least `(member_id, source_epoch, candidate_id,
validation_prediction, pool_position)` and remain immutable after selection.
This matches the candidate identity and order requirements in the related T35
checkpoint review.

### Validation metric

The paper's generic default is the task metric, but the pinned official Churn
run uses **accuracy** as the task score: its validation `score=accuracy=0.87625`,
while `roc-auc=0.8643926187747397`. Its test `score=accuracy=0.857`, while
`roc-auc=0.8585596382206551`. These are main-run evidence, not the conservative
multi-seed paper aggregate. The config has no `task_score` override: the score
comes from dataset metadata via `Task.from_dir`.
This matters because a discrete accuracy score often yields fewer gradual
improvements than a continuous score. The paper explicitly notes that training
loss can sometimes be a better ensemble-selection score.

The local reduced protocol deliberately specifies **validation ROC-AUC** for
checkpoint and greedy choices. This is therefore a documented protocol change
from official Churn, not an inferred official setting. For binary classification,
score averaged **probabilities** (not logits) on the validation split; higher ROC-AUC
is better. Freeze the selected snapshots using validation only, then evaluate the
test split once. Do not use test ROC-AUC to select a checkpoint, break a tie, or
choose ensemble size.

**ROC-AUC label-score ties need a correct independent implementation.** Static
inspection of the pinned `metrics_torch.roc_auc_score` shows descending sorting,
per-row cumulative TPR/FPR, and trapezoidal integration without grouping equal
prediction values. That can differ from standard tie-aware ROC-AUC: a positive
and negative observation with identical scores must contribute half a win, but
an arbitrary within-tie sorted order instead contributes a full win or loss.
The NumPy reporting path uses scikit-learn ROC-AUC. Do not copy the Torch
shortcut into the reduced ROC-AUC selector; use average ranks/grouped thresholds
or a tested library metric consistently for candidate, incumbent, and reported
validation scores. This issue is distinct from ties between candidate ensemble
scores. It was found by source inspection, not by executing upstream code.

## Integration advice

* T16 should expose the validation metric and tie policy as explicit protocol
  fields, use probability averaging, retain candidate rows by `(member_id,
  source_epoch)`, and implement strict improvement both inside a rebuild and
  when accepting a new epoch ensemble.
* Keep a stable ordered candidate list. On equal candidate ensemble scores, use
  individual validation score and then pool order as the official fallback; for
  reproducibility, persist the resulting order and full-precision scores.
* With the reduced four-member/no-pruning setup, do not add finished-member
  candidates unless the implementation actually supports base pruning. Previous
  selected snapshots remain valid candidates even when they share a member ID
  with a current snapshot.
* T35's checkpoint recommendation to persist selected snapshot references,
  source epochs, candidate order, score, and tie rule is consistent with these
  semantics. T23 should include tests for exact ties, equal-to-current strict
  stopping, duplicate member IDs at different epochs, and metric separation
  between validation selection and final test reporting.
* T17/T25 should require standard tie-aware ROC-AUC, including a constant-score
  vector yielding 0.5, mixed-label tied groups, and agreement with an independent
  pairwise oracle. T23 should separately exercise both levels of greedy ties and
  incumbent retention when a rebuild ties or regresses.
