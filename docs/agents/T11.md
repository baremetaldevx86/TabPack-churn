## Compatibility assessment

**CUDA path: compatible for ordinary PyTorch eager FP32 work.** The observed
CUDA 12.8 wheel recognizes compute capability 12.0 and a 128x128 FP32 matmul
completed and synchronized. The reduced protocol's FP32 MLP and packed linear
operations are ordinary ATen/CUDA operations and should fit an 8 GiB card at
the provisional four-member/batch-256 budget, subject to actual feature width,
checkpoint policy, and other desktop GPU use. The available memory probe showed
approximately 8.55 GB decimal bytes reported by PyTorch; `nvidia-smi` showed
8151 MiB total.

**CPU path: required and viable.** The CPU wheel is published for this exact
Windows CPython 3.12 AMD64 ABI, and explicit CPU tensor matmul works. The
reduced run is CPU-friendly enough for smoke tests and small readiness runs,
but full 3-seed/100-epoch measurements will be slower. CPU and CUDA results
must not be mixed in one comparison without recording device, wheel variant,
and timing scope in the manifest. CPU fallback should preserve all model,
seed, split, preprocessing, checkpoint, and selection semantics; only the
device changes.

## Risks and mitigations

1. **Unpinned `torch` selector risk.** `torch>=2,<3` alone does not select the
   intended CUDA or CPU flavor. A generic PyPI install can produce a CPU wheel,
   while a CUDA index can select a CUDA wheel. The final install instructions
   must choose one exact torch version and index/constraints entry per mode,
   then run `pip check` and a tensor/device probe.
2. **CUDA 12.8 versus system CUDA 13.3 display.** `nvidia-smi` reports the
   maximum driver-supported CUDA version, not the runtime bundled by the torch
   wheel. Do not require installing the full CUDA Toolkit: the wheel bundles
   its runtime. If custom CUDA extensions are ever added, toolchain and
   compute-capability support become a separate risk; the current experiment
   should avoid extensions and `torch.compile` requirements.
3. **8 GiB VRAM and WDDM/TDR.** Desktop Windows WDDM shares the GPU with the
   display. Large packed batches, retaining many checkpoint snapshots on GPU,
   or long kernels can cause OOM or a driver/TDR reset. Keep model/checkpoint
   tensors on the selected device deliberately, move frozen snapshots to CPU
   when practical, use modest batch/member settings, and surface OOM as an
   actionable failure. Do not use mixed precision unless separately validated
   for this protocol.
4. **Windows multiprocessing.** PyTorch's Windows FAQ documents `spawn`
   rather than `fork`, requires `if __name__ == '__main__':` protection, and
   says CUDA IPC is unsupported. Start with `DataLoader(num_workers=0)` and
   keep dataset tensors on CPU; avoid sharing CUDA tensors between workers.
   If workers are later enabled, test them independently and retain the main
   guard. This is especially important for a packed ensemble where accidental
   worker/device duplication can exhaust VRAM.
5. **CPU BLAS/thread oversubscription.** The wheel is MKL/AVX2-backed and the
   host has 12 logical CPUs. Cap `OMP_NUM_THREADS`/`MKL_NUM_THREADS` for CI or
   reproducibility probes and record thread settings; do not interpret CPU
   wall-clock results as hardware-independent.
6. **Third-party package drift.** `tabm`, `rtdl_*`, `delu`, Optuna, and
   TensorBoard are mostly Python wheels but transitives include compiled
   packages such as SciPy, scikit-learn, and grpcio. Resolve them in a clean
   Python 3.12 venv, record package metadata/hashes, and run the offline smoke
   tests before any real data run. Do not rely on the global environment.
7. **Current global environment is not a validation environment.** The probes
   prove host capability only. They do not prove that the final package,
   preprocessing, packed optimizer, or selection code is integrated.

## Integration advice

### Device resolution contract

The coordinator should expose an explicit `cpu`, `cuda`, or `auto` choice. A
safe policy is:

- `cpu`: always use `torch.device('cpu')`; never initialize CUDA.
- `cuda`: require `torch.cuda.is_available()`, perform a tiny allocation and
  synchronization, and fail with an actionable diagnostic if it fails. Do not
  silently turn a requested strict CUDA run into a CPU comparison.
- `auto`: try the same CUDA probe once, then emit a structured warning with
  requested/selected device and original error, and continue on CPU if CUDA is
  unavailable. This matches T43's fallback test contract.

The manifest should include requested device, selected device, torch version,
torch CUDA runtime (`torch.version.cuda`), CUDA availability/device count,
device name and capability when applicable, dtype, thread environment, and
whether fallback occurred. A device diagnostic must happen before dataset
workers or model construction.

### Suggested non-training diagnostics

After the isolated install (coordinator-owned; not run here), use commands of
this shape with the final package/CLI substituted:

```powershell
py -3.12 -m venv .venv
& ".\.venv\Scripts\python.exe" -m pip install --require-hashes -r requirements-cpu.txt
# or the separately tested CUDA 12.8 constraints/index for GPU mode
& ".\.venv\Scripts\python.exe" -m pip check
& ".\.venv\Scripts\python.exe" -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
& ".\.venv\Scripts\python.exe" -m <package> preflight --device auto --data-dir <path>
```

The exact lock filenames and package command are intentionally placeholders
until T12/coordinator integration. For CPU CI, install the explicit CPU torch
wheel and set `CUDA_VISIBLE_DEVICES` only as an optional belt-and-suspenders
measure; the application must still select `torch.device('cpu')` explicitly.
Do not use an empty `CUDA_VISIBLE_DEVICES` value as the sole disable mechanism:
the host probe showed that on this Windows setup it did not make
`torch.cuda.is_available()` false.

### Measurement rules

- Run all three model families for a comparison on one selected device and
  report that device in every result.
- Separate CUDA smoke/preflight time from training timing; synchronize around
  CUDA timing boundaries if timing is reported.
- For CPU fallback, rerun the complete requested seed set in a fresh output
  directory rather than mixing partial CUDA and CPU artifacts.
- Preserve T28's isolated-environment and T48 manifest requirements, T43's
  structured fallback diagnostics, and T31's GPU-free CI path.
