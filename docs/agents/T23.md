# T23 — Greedy selector unit-test design

## Assignment

Design focused unit tests for the reduced Churn greedy selector. The tests must
cover the best singleton, genuinely improving additions, strict stopping, no
replacement, deterministic ties, malformed inputs, and validation-only scoring.
This is a test design note; no source or test file was available to edit when
this note was written.

## Sources and evidence

- `swarm.md` decision 8 requires probability averaging, validation ROC-AUC for
  checkpoint/greedy choices, strict improvement, and no replacement. Candidate
  snapshots are distinct rows even when they have the same member ID.
- Read `docs/agents/T3.md`. It records the paper's §3.5 rule (best singleton,
  then the candidate with the best collective score, without replacement, and
  stop if no improvement is possible), plus the official tie fallback: best
  individual score, then stable pool order. It also records strict replacement
  of an online ensemble only on `>` validation improvement.
- The paper's [§3.5 Ensemble](https://arxiv.org/html/2607.05380v1#S3.SS5)
  describes the same greedy primitive. The pinned reference implementation is
  [`src/project/ensemble_utils.py` at
  `05a89e21b955f12de84889d662e15ca534019aaa`](https://raw.githubusercontent.com/yandex-research/tabpack/05a89e21b955f12de84889d662e15ca534019aaa/src/project/ensemble_utils.py).
- Read `docs/agents/T17.md` for the binary ROC-AUC contract, including rejection
  of empty/single-class/nonbinary/nonfinite validation inputs. The fixtures
  below use both classes and therefore avoid an undefined-AUC oracle.

## Proposed test seam

Adapt names to T16's final API. The tests need a pure function with equivalent
semantics to one of the following forms:

```python
select_greedy(
    predictions, *, score_fn, max_ensemble_size,
    prediction_scores=None, with_replacement=False,
) -> SelectionResult
```

or a public wrapper that accepts `(y_true, probabilities)` and supplies the
ROC-AUC score function. `predictions` should be shaped `(n_candidates,
n_validation_rows)`; the selected ensemble prediction is the arithmetic mean
of selected **probabilities**. The result must expose ordered candidate rows,
the final validation score, and, if supported, the score after each accepted
addition. A list of indices is sufficient if the implementation does not use a
result object. Tests should compare candidate row/snapshot identity, not only
member IDs.

All expected values below use labels
`y = [0, 0, 0, 1, 1, 1]` and predictions formed as `integer_grid / 16`.
Using integer-scaled probabilities makes the fixtures reproducible while AUC
depends only on their ordering. The test score function should be the project's
binary ROC-AUC implementation, or an equivalent independent test oracle; do
not use the selector's own score calculation to manufacture expected values.

## Exact behavioral tests

### 1. Best singleton is selected first

Use:

```text
candidate 0: [11, 13,  2,  5,  7, 12] / 16   AUC = 4/9
candidate 1: [10,  3, 14, 11,  5, 13] / 16   AUC = 5/9
candidate 2: [ 2,  1, 12,  9, 14, 12] / 16   AUC = 5/6
candidate 3: [ 9,  4, 12, 14,  6,  5] / 16   AUC = 5/9
```

With `max_ensemble_size=1`, assert selected rows are `[2]` and the score is
`5/6`. This catches accidental first-row selection, sorting in ascending
direction, and selecting by the best future pair rather than the required best
singleton. With a larger size, the first selected row must still be `2`.

### 2. Additions are chosen by collective improvement, not individual score

Using the same four rows and `max_ensemble_size=3`, assert the ordered result
is `[2, 0, 3]`. The validation scores after each accepted selection are:

```text
[2]       -> 5/6
[2, 0]    -> 8/9
[2, 0, 3] -> 1
```

At the first addition, candidate 0 gives `8/9`; candidates 1 and 3 each give
`2/3`. At the next addition, candidate 3 gives `1`, while candidate 1 gives
`7/9`. This proves the loop evaluates the average of the current ensemble plus
each unused candidate and does not simply append candidates in individual-AUC
order. Also assert each accepted score is strictly greater than its previous
score.

### 3. Strict stop rejects equal or worse additions (including look-ahead)

Use:

```text
candidate 0: [12,  5,  9, 15,  9,  5] / 16   AUC = 5/9
candidate 1: [15, 10,  7,  2,  5, 14] / 16   AUC = 2/9
candidate 2: [14,  4,  4, 10, 12,  2] / 16   AUC = 4/9
```

Both possible additions to the best singleton have score `4/9`, which is not
strictly greater than `5/9`. With `max_ensemble_size=3`, assert the selector
returns only `[0]` and `5/9`; it must not add an equal-scoring candidate. The
three-way average happens to score `2/3`, so this fixture also guards against a
non-greedy look-ahead that skips a non-improving step to reach a larger
ensemble. An online wrapper should likewise retain the previous epoch's
selection when a rebuilt selection has exactly the stored validation score.

### 4. No replacement means each candidate row can occur once

Use:

```text
candidate 0: [13,  6,  5,  5, 12, 14] / 16   AUC = 11/18
candidate 1: [ 5, 12,  6, 10, 13,  4] / 16   AUC = 5/9
```

For `with_replacement=False`, `max_ensemble_size=3`, assert the result is
`[0, 1]`, with score `2/3`, and contains no duplicate index. There are no
unused rows after those two selections, so the selector must stop rather than
re-use row 0. For an implementation that exposes replacement as a separate
debug/reference mode, the same fixture is an oracle for the distinction:
allowing replacement can select `[0, 0, 1]` with score `7/9`, whereas the
reduced protocol must never do so. If replacement is not public, retain only
the no-replacement assertion and inspect the internal candidate mask through a
test seam rather than changing production policy.

Candidate identity is the row/snapshot identity. A second row with the same
`member_id` but a different epoch is still a legal distinct candidate; no
replacement prevents selecting that row twice, not selecting the same member
ID across different snapshots.

### 5. Ties are deterministic and follow the documented fallback

Parameterize the following cases:

1. **Initial singleton tie:** duplicate the best row in positions 0 and 1,
   request size 1, and assert position 0 wins. This verifies stable pool order.
2. **Extension tie resolved by individual score:**

   ```text
   candidate 0: [ 1,  1,  4,  4, 12,  8] / 16   AUC = 17/18
   candidate 1: [10, 15,  3, 14, 10, 13] / 16   AUC = 11/18
   candidate 2: [11,  3,  1, 10,  5,  9] / 16   AUC = 2/3
   ```

   Both `[0, 1]` and `[0, 2]` score `1`, but candidate 2 has the better
   individual score. With size 2, assert `[0, 2]`, not `[0, 1]`.
3. **Extension tie resolved by pool order after individual tie:** use the
   no-replacement row 0 above and put two identical copies of row 1 in
   positions 1 and 2. Both additions have score `2/3` and equal individual
   score `5/9`; assert `[0, 1]`. Permuting the two identical rows should move
   the selected position with the pool, proving no hash/set ordering is used.

Use exact `>`/`<=` semantics for acceptance, with no tolerance that turns an
equal score into an improvement. Run each tie case twice and assert identical
ordered output and score. If result metadata includes a tie-break reason, assert
the expected reason (`individual_score`, then `pool_order`).

## Invalid-input and invariant tests

These should fail before selection with a clear `ValueError` (or the project's
documented validation exception), rather than an `IndexError`, empty reduction,
or silent coercion:

| Input | Expected rejection |
| --- | --- |
| zero candidate rows, e.g. shape `(0, 6)` | no singleton exists |
| one-dimensional, three-dimensional, or ragged predictions | predictions are not a rectangular 2-D pool |
| any NaN, `+inf`, or `-inf` prediction | invalid probability input |
| `max_ensemble_size=0` or a negative value | ensemble size must be positive |
| non-integral or boolean ensemble size | invalid size type |
| `max_ensemble_size > n_candidates` (if the API promises strict bounds) | impossible requested size; do not hit an empty candidate reduction |
| `prediction_scores` with wrong length, NaN, or infinity | invalid tie-break scores |
| score function returning wrong length, nonfinite values, or a scalar | invalid scoring contract |
| `with_replacement=True` when the reduced selector forbids it | unsupported protocol mode |

If the public wrapper owns `y_true`, additionally pass empty labels, unequal
label/prediction lengths, nonbinary labels, NaN labels/scores, and a
single-class validation split. These must propagate the binary metric's
validation error; do not substitute AUC `0.5`. If `max_ensemble_size > n` is
instead deliberately documented as “cap at n”, change that one expectation to
the cap behavior and assert the result remains unique.

For every successful case, also assert the selector does not mutate the input
prediction array or caller-owned `prediction_scores`, returns indices in the
candidate pool range, returns a finite score, and returns no duplicate rows in
no-replacement mode. A repeated call on the same arrays must produce identical
indices, score, and tie outcome.

## Test organization and execution

Suggested file: `tests/test_greedy_selector.py`, with one test per numbered
behavior and a parameterized invalid-input test. Keep the fixtures small and
CPU-only. Use an independent local AUC oracle or the metric test oracle from
T17, not a second call through the selector. Run after implementation with:

```text
python -m pytest tests/test_greedy_selector.py -q
```

At this repository state there is no implementation, dependency environment, or
pytest configuration, so no tests were run and no installation was attempted.

## Integration advice and coordination

- **T16:** expose a stable ordered candidate sequence and a narrow pure selector
  seam. Preserve row/snapshot identity, use probability means, and make the
  strict-improvement and tie policy explicit in the result/configuration.
- **T3:** this note incorporates the requested tests for equal-to-current stop,
  exact tie fallback, and same-member/different-epoch candidate identity.
- **T17/T25:** validation errors should remain strict and metric-independent;
  selection must never turn malformed or single-class validation data into an
  apparently good candidate.
- **T35/T42:** selection metadata should retain source epoch/member ID and pool
  position so these unit tests can assert snapshot identity and deterministic
  replay without relying on serialized object ordering.
