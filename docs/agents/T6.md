The official README says to compute published metrics from the **evaluation** report by taking each experiment's `metrics.test.score` and using the arithmetic mean and `statistics.stdev` (sample SD). Calculations use `mean = sum(x_i) / 5` and `sample_sd = sqrt(sum((x_i - mean)^2) / (5 - 1))`; values above are shown to more precision than the paper only to make provenance checks possible. In the official report, `metrics.*.score` is equal to `accuracy`, while `roc-auc` is a separately reported metric. For example, the standard TabPack main report's final seed-0 online ensemble has validation accuracy 0.87625, test accuracy 0.85700, validation ROC-AUC 0.8643926, and test ROC-AUC 0.8585596; this single main run must not be substituted for the five-run evaluation aggregate.

The pinned evaluation config/report discrepancy should be recorded: Appendix F.1/Table 14 prose says “ten random seeds,” but the pinned evaluation configs explicitly say `n_seeds: 5`, and the five report values above reproduce the printed Table 14 means and sample SDs. Cite the artifact as five runs unless the upstream provenance is resolved; do not claim a ten-seed local reproduction from these files.

## Comparability limits for the local reduced experiment

The official rows are a useful reference point, not a reproduction target for the ledger's reduced experiment. Relevant differences are:

1. **Metric and selection:** official Churn `score` is accuracy (the pinned reports also expose ROC-AUC). The reduced protocol selects checkpoints/ensembles by validation ROC-AUC. A local ROC-AUC result must not be compared numerically to Table 14 accuracy.
2. **Evaluation protocol:** the paper uses tuned baselines and the conservative TabPack protocol (one main selection run followed by evaluation runs with selected configurations), while the ledger explicitly calls its repeated full candidate-training workflow a reduced optimistic protocol. This changes the amount of validation-driven exploration per seed.
3. **Seeds:** Table 14 text says ten seeds; the pinned TabPack evaluation configs contain five seeds; the local reduced protocol has three seeds `[0, 1, 2]`. Mean/SD across these sets are not interchangeable.
4. **Model and optimizer:** official plain TabPack samples depth 1–4 at fixed width 384; the dagger configuration samples depth 1–3 at fixed width 384 and uses cosine feature embeddings. Official training uses `MuonAdamWPack`; the reduced local methods use plain MLPs, small widths `[32, 64, 96]`, at most four members, no embeddings, and AdamW.
5. **Data processing and precision:** the pinned Churn configs explicitly use `num_policy: noisy-quantile`, `extract_bin_from_num: true`, `bin_policy: convert-to-cat`, and `cat_policy: ordinal`, plus bfloat16. The paper's general F.1 prose describes quantile normalization and one-hot encoding. The reduced ledger specifies train-only median imputation, quantile-normal transform, one-hot encoding, and float32. These are declared protocol changes, even where the batch size 256 matches the pinned config rather than Table 5's listed 128.
6. **Capacity/compute:** official runs use 64 sampled base models (with official early stopping/pruning behavior) and up to 32 selected snapshots, on A100/MacBook hardware. The local comparison uses four candidates and max four selected snapshots on Windows CPU/CUDA hardware. Equal local epochs and per-member batches do not equal official FLOPs, parameters, memory, or wall time.
7. **Attribution:** the three local methods change multiple factors together (packing, heterogeneity, candidate count, capacity, optimizer, selection metric, and checkpoint policy). Any local difference cannot be attributed to packing or hyperparameter diversity alone. One Churn split also cannot support the paper's across-dataset claims.
