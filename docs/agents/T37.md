# T37 — Reproducible benchmark timing design

## Assignment and scope

Design a timing protocol for the three reduced Churn comparisons:

1. one ordinary MLP;
2. four independently trained homogeneous MLP members; and
3. the four-member heterogeneous packed TabPack-style model.

This is a documentation-only review. It does not add a timer, run training,
install packages, or report measurements. The protocol below is intended to be
implemented by the coordinator and recorded in each result artifact.

## Evidence and related notes

I read `swarm.md`, including decisions 6–8, and the related notes `T20`,
`T35`, `T36`, and `T48` before finishing. T20 already defines `fit_wall_s`,
`final_test_predict_wall_s`, `final_test_metrics_wall_s`, `run_wall_s`, and a
`timing_protocol_id`; this note supplies the boundary and synchronization
semantics for those fields. T35 requires selection to be frozen before test
evaluation, and T48 requires monotonic durations plus a documented
warmup/synchronization policy.

The PyTorch CUDA semantics documentation states that CUDA work is asynchronous
and that unsynchronized CPU timestamps are inaccurate; it recommends either
`torch.cuda.synchronize()` or timed `torch.cuda.Event` pairs:

* https://docs.pytorch.org/docs/2.11/notes/cuda.html#asynchronous-execution
* https://docs.pytorch.org/docs/2.11/generated/torch.cuda.Event.html

Python 3.12 documents `time.perf_counter_ns()` as a high-resolution,
monotonic elapsed-time clock:

* https://docs.python.org/3.12/library/time.html#time.perf_counter_ns

## 1. Timing quantities and exact boundaries

Use seconds as the persisted unit and retain integer nanosecond boundaries in
an optional diagnostic record. Every elapsed interval is
`(perf_counter_ns_end - perf_counter_ns_start) / 1e9`; never use wall-calendar
`time.time()` for a duration.

### Required primary measurements

| Field | Start boundary | End boundary | Scope |
| --- | --- | --- | --- |
| `setup_wall_s` | process/setup phase begins | model, optimizer, loaders, and required input tensors are ready | Construction and runtime initialization; preprocessing/download are separate. |
| `fit_wall_s` | immediately before the first configured training operation/epoch | after the last member has stopped and validation-driven checkpoint/greedy selection is frozen | Training, validation, checkpoint decisions, and selection; no test labels or test prediction. |
| `final_test_predict_wall_s` | frozen predictor receives the first preprocessed host test batch | complete host probability-averaged predictions are ready | Operational inference including batch staging, transfers, sigmoid and averaging; metric calculation is separate. |
| `final_test_metrics_wall_s` | predictions and labels are available to the metric implementation | ROC-AUC and log-loss for the frozen test predictor are complete | CPU metric work only; do not include model forward or output transfer. |
| `run_wall_s` | application entry before setup | result payload is ready, before terminal timing/result JSON is written | Independent enclosing duration including measured setup, fit, evaluation and earlier artifact work; excludes imports before entry and final self-report serialization. |

The three methods must use the same dataset/splits, train-fitted
preprocessing, batch size, epoch/patience limits, dtype, device policy, input
pipeline settings, and timing boundaries. `fit_wall_s` is an elapsed execution
path, not a sum of per-member times. In particular, do not divide homogeneous
ensemble time by four and do not sum overlapping packed-member times. Record
whether members were executed serially or concurrently.

Optional `validation_wall_s`, `selection_wall_s` and in-fit checkpoint-write
durations are children of `fit_wall_s`; do not add them a second time. Selection
timing starts after candidate validation predictions are ready. Necessary
snapshot copies and checkpoint writes inside fit remain charged to fit. A
supervisor may separately measure launch-through-exit CLI time, including
imports and final writes, under `cli_wall_s`; this is not `run_wall_s`.

Preprocessing and download are shared experiment costs and are not charged to
one method. If a method has extra method-specific setup, keep it in that
method's `setup_wall_s` and do not hide it in `fit_wall_s`. Freeze selection
before starting any final-test timer, as required by the evaluation protocol.

### Optional CUDA timeline measurements

`fit_wall_s` is the authoritative training comparison because it includes
Python scheduling, data-loader work, CPU validation/selection, transfers, and
CUDA execution. An optional `fit_gpu_event_s` may measure the device timeline
between a CUDA start/end event, but it is a diagnostic elapsed-stream interval;
it must not replace `fit_wall_s` or be presented as total training time. It
can be `null` for CPU runs or implementations that use unsupported streams.

For inference, record both measurements when CUDA is available:

* `final_test_predict_wall_s`: operational host-to-host elapsed time with
  synchronization at both boundaries, including T36's prescribed host float64
  probability computation if adopted;
* `forward_device_wall_s` and `forward_device_event_s`: a separate repeatable
  device-resident forward workload that produces all selected-member logits;
  both divided by the same number of repetitions.

CUDA events timestamp the device timeline. Their interval can include idle
gaps while the host launches work or computes between records: it is **not
pure kernel execution time, GPU busy time, utilization, or CPU time**. They
also exclude CPU work occurring outside the event interval. Never subtract
event time from wall time to infer CPU overhead. A profiler would be needed
for kernel-active accounting and is outside this bounded protocol. Label the
two endpoints `host_features_to_host_probabilities` and
`device_features_to_member_logits`; never compute ratios across endpoints.

## 2. CPU wall-clock procedure

1. Resolve the device and all protocol settings before the timed region. Set
   fixed PyTorch intra-op/inter-op thread counts and fixed data-loader worker
   settings; record effective values in provenance. Do not change them between
   methods.
2. Materialize the identical transformed split. For training, use independent
   deterministic per-member permutations as required by the protocol, with
   corresponding member streams reused only when scientifically comparable.
   Do not force all ensemble members to use one shared batch. For inference,
   use exactly the same batch schedule across methods. Shared preprocessing,
   download, and input construction are outside `fit_wall_s`; fit includes
   permutation generation, batch gathering and transfers performed in the loop.
3. Call `time.perf_counter_ns()` immediately at the declared start and end.
   Keep the timer in the same process/thread; do not use process CPU time,
   calendar time, logging timestamps, or rounded display values.
4. On CPU, no synchronization call is needed. On CUDA, apply the boundary
   procedure in section 3 even when the result is persisted as wall time.

Record `clock_resolution` from `time.get_clock_info("perf_counter")`, the
effective thread/worker counts, and a sanitized concurrent-load observation
(`none`, `detected`, or `unknown`). CPU wall time includes OS scheduling and
other load by design; three seeds provide descriptive dispersion, not a claim
of identical runtimes.

## 3. CUDA wall-clock and event procedure

The default protocol uses one device and its default/current stream. A fresh
process per `(seed, method)` is preferred so CUDA context creation, allocator
state, caches, and failed-run residue cannot leak between comparisons. Process
startup before application entry is outside `run_wall_s` and may be measured
by `cli_wall_s`; device initialization and method setup are included in
`setup_wall_s`. Fresh processes do not reset driver caches or GPU temperature.

### Wall-clock boundaries

For every CUDA-touched timed interval:

```text
torch.cuda.synchronize(device)       # drain work submitted before start
wall_start = time.perf_counter_ns()
run measured region
torch.cuda.synchronize(device)       # drain all work from measured region
wall_end = time.perf_counter_ns()
```

The first synchronization prevents earlier queued work from contaminating the
start, and the second prevents asynchronous work from being charged to a later
phase. Do not synchronize every training batch merely to make execution look
synchronous; that changes the workload and can materially distort `fit_wall_s`.
If a non-default stream is used, either reject the run under this protocol or
join/synchronize every participating stream at both boundaries and record the
stream policy. Synchronizing only the default stream is insufficient for
independent side streams.

Do not set `CUDA_LAUNCH_BLOCKING=1` for primary measurements. It serializes
launch behavior and is a debugging mode, not an equivalent timing protocol.
It may be used only for a separately labelled diagnostic run.

### CUDA event boundaries

Create and record the timed events once before measurement and synchronize to
initialize their lazy CUDA resources. For a device-resident predictor on the
current stream, reuse those primed events for each block:

```text
torch.cuda.synchronize(device)
wall_start = time.perf_counter_ns()
start_event.record(current_stream)
repeat the fixed predictor workload
end_event.record(current_stream)
torch.cuda.synchronize(device)
wall_end = time.perf_counter_ns()
gpu_seconds = start_event.elapsed_time(end_event) / 1000 / repetitions
wall_seconds = (wall_end - wall_start) / 1e9 / repetitions
```

The stream/device for both events must match. Record the event timing in
addition to host wall timing; do not call `elapsed_time` before the end event
has completed. If data transfers are part of the selected endpoint, enqueue
them on the same stream and include them between the event records, or use the
explicit host/device wall endpoint instead. A side stream requires an explicit
join event or a separate stream timing design and must not silently report a
partial event interval.

For fit diagnostics, events span the declared fit workload. Host-side
validation/selection between the records can leave gaps on that device
timeline, so the enclosing event interval may approach fit wall time even
when GPU utilization is low. Prefer `fit_gpu_event_s: null` unless this limited
meaning is useful; the fixed-work forward/update diagnostics below are more
interpretable. Device-wide synchronization waits for all streams of this
process, but does not make unrelated processes stop using the GPU.

## 4. Warmup rules

Warmup is part of the timing protocol and must be stored as structured fields,
not left implicit.

### Training/fit

The default is **no discarded training warmup**. `fit_wall_s` starts with the
first configured optimizer-visible training operation and counts every actual
epoch, batch, validation pass, checkpoint decision, and greedy selection step.
Discarding a training epoch would alter optimizer state, dropout/RNG streams,
data order, early stopping, and the scientific work being compared.

Before this timer, the runner may perform common device initialization (for
example, selecting the device, allocating a small sentinel, and synchronizing)
as part of setup. A method-specific forward/backward warmup is allowed only if
it is declared in the manifest, performed before the fit boundary, and has no
effect on the measured run: use a throwaway clone or save/restore all model,
optimizer, gradient, sampler, and RNG states. The default should avoid this
complexity. Never warm up only the packed model or only one baseline.

### Supplementary fixed-work training timing

Early stopping and heterogeneous capacity make fit time a quality/cost
comparison, not a clean measure of the speed gained from packing. For a
bounded systems diagnostic, use disposable models with the actual sampled
configurations, 10 untimed training supersteps, then five timed blocks of 20
supersteps. A superstep updates **every** member once using `B=256` rows per
member, including gather, forward, sample-mean/member-sum loss, backward and
the configured AdamW update. The ordinary MLP updates one member. Keep all
members active for this diagnostic; persist exact update counts and inputs.

Restore the same post-warmup model, optimizer, explicit/global RNG states and
batch cursor before each measured block, outside its timer, then synchronize.
Warmups and fixed-work updates are never used for scientific scores, selection
or epochs. Report `step_wall_s`, `step_event_s`, rows per member, member-update
count and logical member-examples/s; do not conflate `4B` member-example work
with `4B` distinct input rows. Mark short/noisy blocks as diagnostic rather
than extending training invisibly. These proposed 110 updates per member
remain a separate optional budget for the coordinator to accept.

The homogeneous-versus-heterogeneous comparison changes capacity as well as
execution. A claim that packing itself causes a speedup additionally requires
looped execution of the **same heterogeneous member configurations**, weights,
batch schedules and optimizer policy as the packed model; this is an optional
control, not a fourth required scientific model. Record active and padded
parameter sizes and epochs/updates for each main method (coordinate with T46).

### Frozen final-test prediction

Use the same immutable, preprocessed test batch schedule for all methods,
`model.eval()` and `torch.inference_mode()`, with no parameter or sampler
updates. The recommended fixed protocol is:

* `warmup_repetitions = 10` complete predictor passes;
* `measurement_repetitions = 30` complete predictor passes, divided into five
  deterministic blocks of six;
* no test metric computation during warmup or measurement; retain predictions
  from the last measured pass and compute the scientific test metrics once,
  outside timing. Repeated inference does not reopen selection.

Warmup passes run after the frozen checkpoint is loaded and before timing. On
CUDA, synchronize after the final warmup. Measure all blocks with the same
batch order and endpoint. Persist per-block wall and event values, then report
the arithmetic mean and (preferably) median of per-pass values; do not report
only the fastest block. Check shape/finiteness after a representative untimed
warmup and after the final measured block, avoiding extra per-pass host
synchronization. Retain only the final required output; ordinary intermediate
allocation/freeing remains part of the workload. A small fixed
batch is acceptable only for a separately labelled microbenchmark; it must not
be called full-test prediction timing.

If inference uses stochastic behavior despite `eval()` (for example, an
intentional stochastic layer), save and restore the prescribed RNG around
warmup and use the same fixed random stream for every method. The reduced
protocol has ordinary dropout during training but should have deterministic
inference after `eval()`.

Record block durations: if six passes are too short for a credible wall-time
sample (proposed floor 100 ms), label that result `short_block`. A separate,
predeclared longer-repeat benchmark may be used, but must record its different
repetition count/protocol and include every method. Do not silently choose the
fastest repetitions or turn 30 passes into 30 independent scientific seeds.

Inference must actually execute every selected snapshot and probability
average on each pass. Reusing cached predictions measures a lookup. Distinct
epochs of the same base member are separate snapshots. Load the final frozen
predictor before warmup and record selected snapshot count, layout and any
packing/repacking setup time. Do not claim deployed packed speed if the final
predictor actually executes extracted members serially.

## 5. Fairness, ordering, and reporting

* Run the same `(seed, method)` matrix on matching hardware/software and keep
  device, driver, CUDA runtime, dtype, TF32, deterministic-algorithm,
  thread/worker, batch-size, and timing protocol IDs in every result.
* Use a predeclared counterbalanced method order if multiple runs share a
  process/GPU, for example: seed 0 `[mlp, independent, packed]`, seed 1
  `[independent, packed, mlp]`, seed 2 `[packed, mlp, independent]`. Prefer a
  fresh process regardless. Never reorder after seeing results.
* Keep model construction, checkpoint restore, preprocessing, and final metric
  work out of the predictor timer, or include them for every method under a
  separately named endpoint. Do not mix cold-start and warmed measurements.
* Report each seed/method value, then unweighted mean and sample SD across the
  three seeds as T20 specifies. A speedup is defined only for matched seed,
  hardware, endpoint, and timing protocol; retain both the mean of per-seed
  ratios and the ratio of means if both are shown. Timing does not establish a
  quality winner.
* Record interruptions, OOMs, thermal/concurrent-load changes, and resumed
  invocations as diagnostics. A resumed fit is not a clean timing comparison;
  aggregate all work only under T20/T48's explicit resume rules.
* On the laptop, keep AC power and OS/vendor performance mode consistent;
  record the mode, observed GPU temperature/clock if available, and unknowns.
  Run one benchmark at a time after unrelated training/tests finish. Use a
  fixed, recorded inter-run idle interval (proposed 30 seconds), recognizing
  that it does not guarantee equal thermal state. Do not lock clocks/change
  power limits automatically, flush allocator caches between timed blocks,
  enable a profiler, or autotune per-method CPU threads during primary runs.

Suggested `timing` fields (names can be adapted to the coordinator's final
schema) are:

```json
{
  "timing_protocol_id": "wall-v1-cuda-events-v1",
  "clock": "time.perf_counter_ns",
  "clock_resolution_s": null,
  "fit_wall_s": null,
  "fit_gpu_event_s": null,
  "final_test_predict_wall_s": null,
  "forward_device_wall_s": null,
  "forward_device_event_s": null,
  "final_test_metrics_wall_s": null,
  "predict_endpoint": "host_features_to_host_probabilities",
  "warmup_repetitions": 10,
  "measurement_repetitions": 30,
  "measurement_blocks": 5,
  "cuda_boundary_sync": true,
  "cuda_event_stream": "current_default",
  "training_warmup": "none",
  "member_execution": "serial"
}
```

This is a configuration/schema example with measurements deliberately absent.
Clock resolution must be observed; nanosecond return units do not imply
nanosecond hardware resolution. Persist null for an unavailable event or phase;
never substitute zero. CPU runs set CUDA/event fields to null/not applicable.

## 6. Acceptance checks for integration

1. A CPU timing fixture uses `perf_counter_ns`, returns nonnegative finite
   seconds, and preserves the declared boundary fields. A backwards-calendar
   clock cannot affect the duration.
2. A CUDA fixture (when available) verifies pre-sync, clock/event start,
   workload, event end, post-sync, then clock/end-event reading in that order.
   Assert positive finite times for bounded nontrivial work, without fragile
   absolute latency or exact event-to-wall equality assertions.
3. CPU and CUDA paths use the same fixed input batches, repetitions, endpoint,
   and output shape. CUDA event milliseconds are converted to seconds exactly
   once, and host wall time is not replaced by event time.
4. A training fixture verifies that no discarded warmup changes model,
   optimizer, sampler, dropout/RNG, or epoch counters. A declared throwaway
   warmup cannot change the subsequent configured run.
5. A frozen predictor fixture performs exactly 10 warmups and 30 measured
   full-test passes, with five blocks of six and no metric calculation inside
   the measured region. Warmup and measurement predictions do not alter the
   checkpoint or selection.
6. Aggregation rejects comparisons with mismatched endpoint, device, dtype,
   synchronization policy, warmup count, or timing protocol ID; it retains
   per-block values and reports mean/sample SD across seeds.
7. A multi-stream event fixture is rejected or explicitly joined before the
   end event; a default-stream event must not certify unjoined side-stream
   work. Device-wide wall synchronization does cover those streams.
8. A resumed/failed run carries timing diagnostics and is excluded from clean
   runtime summaries unless the manifest explicitly accepts its timing scope.
