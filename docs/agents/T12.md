# T12 — Minimal pinned dependency and reproducibility strategy

## Assignment

Research a small, pinned environment for the independent Churn experiment on
CPython 3.12/Windows AMD64 with either CPU or CUDA, without installing
anything, training, or changing implementation files.

## Recommended dependency layers

Keep the direct runtime set intentionally small:

Pin the reference interpreter to **CPython 3.12.10, 64-bit Windows AMD64**;
declare project support as `>=3.12,<3.13` until another minor is tested. The
launcher selector `py -3.12` is not itself a patch-version guarantee: assert
the resulting interpreter version and record any deliberate patch upgrade.

```text
numpy==2.2.6
scipy==1.15.3
scikit-learn==1.6.1
torch==2.11.0+cpu       # CPU lock only
torch==2.11.0+cu128     # CUDA lock only
```

`scikit-learn` brings its required `joblib` and `threadpoolctl`; SciPy and
PyTorch bring their own transitive runtime requirements. Published Windows
torch 2.11.0 metadata requires `filelock`, `typing-extensions>=4.10.0`,
`setuptools<82`, `sympy>=1.13.3`, `networkx>=2.5.1`, `jinja2`, and
`fsspec>=0.8.5`; include all resolved pins/hashes (including `setuptools`) in
the lock. Do not add pandas,
TensorBoard, Optuna, `tabm`, `rtdl_*`, `delu`, Muon, torchvision, or torchaudio
unless an implementation task proves a direct need. They are not needed for
the reduced, independently authored Churn comparison and would enlarge the
lock and platform surface. Keep test/tool dependencies out of the measured
runtime lock:

```text
pytest==8.4.2
ruff==0.12.12
mypy==1.17.1       # optional quality extra, if type checking is adopted
```

The versions above have compatible Python 3.12 Windows wheels; their
transitives must still be resolved and hashed into the dev lock. A pinned
bootstrap may use `pip==25.2` and an ephemeral `pip-tools==7.5.0`; neither is
an experiment dependency. Keep the resolver's own transitive bootstrap lock
separate. If setuptools is the selected project backend, `setuptools==80.9.0`
satisfies torch's cap; `wheel==0.45.1` is a compatible build-tool pin. Install
the independently authored local package separately with `--no-deps
--no-build-isolation` after the hashed runtime/build-tool locks, or use its
documented source entrypoint. Do not place a mutable local/editable project
requirement inside a hash-enforced third-party dependency lock.

## Two locks, one code path

Commit the declarative inputs and generated locks (names are proposals for the
coordinator):

```text
requirements/
  py312-win.in             # NumPy/SciPy/sklearn and setuptools pin
  py312-win-cpu.in         # includes the CPU torch selector
  py312-win-cu128.in       # includes the CUDA 12.8 torch selector
  py312-win-cpu.txt        # fully resolved, hashed runtime lock
  py312-win-cu128.txt      # fully resolved, hashed runtime lock
  py312-win-dev.txt        # CPU lock constrained with pytest/quality tools
```

Compile CPU and CUDA locks independently under CPython 3.12 on Windows AMD64.
Prefer putting the exact official torch wheel URL from the selected index in
the flavor input (`torch @ https://.../torch-2.11.0%2Bcpu-cp312-cp312-win_amd64.whl`
or its `cu128` equivalent), with the observed hash retained in the final lock.
Resolve other packages from PyPI; a direct torch URL avoids mixing two general
package indexes. The URL must be copied from the index and checked, not the
illustrative abbreviated URL here. Example compilation commands, not run:

```powershell
python -m piptools compile --generate-hashes --allow-unsafe `
  --index-url https://pypi.org/simple --pip-args "--only-binary=:all:" `
  --output-file requirements/py312-win-cpu.txt requirements/py312-win-cpu.in

python -m piptools compile --generate-hashes --allow-unsafe `
  --index-url https://pypi.org/simple --pip-args "--only-binary=:all:" `
  --output-file requirements/py312-win-cu128.txt requirements/py312-win-cu128.in
```

The exact compile command, index URLs, resolver version, target tags
(`cp312-cp312-win_amd64`), and UTC generation time belong in each generated
lock header. Because pip-tools resolves environment markers against the
interpreter that runs it, regenerate each lock with Python 3.12 Windows rather
than compiling once on Linux. `--allow-unsafe` ensures pip-tools also emits
the required setuptools pin/hash; this flag is the resolver's historical name,
not permission to bypass hash checks. Generated locks should contain hashes
for every selected wheel and should be installed with
`--require-hashes --only-binary=:all:`. These proposed pins and observed hashes
are metadata evidence, not a completed or tested lock. All transitives and
wheel downloads still require coordinator verification.

The venv sequence is intentionally direct and PowerShell-portable:

```powershell
py -3.12 -m venv .venv
& .\.venv\Scripts\python.exe -m pip install --upgrade pip==25.2
& .\.venv\Scripts\python.exe -m pip install --require-hashes --only-binary=:all: `
  -r requirements\py312-win-cpu.txt
```

Use the CUDA lock instead when `--device cuda` is requested. Calling the venv
interpreter directly avoids PowerShell execution-policy/activation issues.
Do not install both torch variants in one environment. A generic `device=auto`
must report whether CUDA is actually available and record CPU fallback; the
presence of a `+cu128` wheel alone is not proof of a usable driver/GPU.

## Tests and acceptance checks

The lock strategy is accepted only after a fresh venv passes all of these
short checks; no Churn download or long training is involved:

1. Install from the selected lock with `--require-hashes --only-binary=:all:`;
   run `python -m pip check` and fail on dependency conflicts.
2. Run a version/build assertion that prints (without secrets) Python version,
   package versions, `torch.__version__`, `torch.version.cuda`,
   `torch.backends.cudnn.version()`, and `torch.cuda.is_available()`. A CPU
   lock must have `torch.version.cuda is None`; a CUDA lock may have `+cu128`
   but GPU tests must explicitly skip when unavailable and an explicitly
   requested CUDA experiment must fail clearly. A CPU execution under the
   CUDA lock is valid if recorded and must not be mistaken for a CPU-wheel run.
3. Run the offline synthetic smoke suite from T31/T42 with explicit CPU and no
   network/data markers: preprocessing fit/transform, one packed and ordinary
   forward/backward step, probability/metric output, and selection plumbing.
   This validates imports and wheel compatibility, not scientific Churn
   evidence.
4. On a CUDA-capable host, add one marked `gpu` test that allocates a tiny
   tensor, performs one forward/backward step, synchronizes, and releases it.
   Keep it separate from mandatory CPU CI; do not require a GPU runner.
5. Re-run the deterministic unit/equivalence suites with `OMP_NUM_THREADS=2`,
   `MKL_NUM_THREADS=2`, fixed `PYTHONHASHSEED`, explicit CPU, and the project's
   seed/determinism policy. T21/T22 should compare packed and independent
   operations within documented float32 tolerances.
6. Verify lock provenance: recompute each lock file's SHA-256, confirm every
   installed runtime distribution matches a lock pin (with bootstrap tools and
   the local source package accounted for separately), and record the lock relative
   path plus digest in `provenance.json`. Record active-interpreter versions
   from `importlib.metadata`, torch build suffix, CUDA build, cuDNN, driver,
   requested device, and actual device separately. Do not serialize raw
   `pip freeze`, environment variables, credentials, absolute paths, or URLs
   containing tokens.

CI should use the Windows CPU lock explicitly on Windows. T31's Linux leg
needs its own CPython 3.12 Linux CPU lock, resolved and validated on Linux;
Windows direct wheel URLs cannot be reused there. Set
`CUDA_VISIBLE_DEVICES=''` and run the T31 smoke/unit commands offline after
dependency installation. CUDA compatibility is a local preflight concern.

For repeatability, use explicit member RNG streams, preprocessing random
state, float32, fixed thread counts, `num_workers=0` for this small Windows
experiment, deterministic algorithms, disabled cuDNN benchmarking, and a
recorded TF32 policy. T11/T34 should settle any CUDA workspace setting before
initialization. [PyTorch 2.11 reproducibility guidance](https://docs.pytorch.org/docs/2.11/notes/randomness.html)
explicitly disclaims cross-platform/release and CPU/GPU exact equivalence:
test repeatability within the locked environment and device, and use numerical
tolerances for cross-device equivalence instead of promising bitwise equality.

## Provenance and update policy

The lock is a reproducibility input, not a substitute for a run manifest. For
each run, capture the lock file SHA-256, the exact installed package name and
version set, Python implementation/build, OS/architecture, torch CUDA build,
actual driver/GPU availability, and the source/config/data identities required
by T48. Preserve the selected CPU/CUDA lock as a repository artifact; never
claim that the CPU and CUDA environments are byte-identical. Their Python and
non-torch pins should normally match, while the torch wheel and any resolver
differences remain explicit.

Dependency updates should be deliberate: update one direct pin or the torch
flavor, compile both target locks in clean Python 3.12 Windows environments,
review the dependency diff and hashes, rerun lock/install/smoke checks, then
record the lock digest and rationale in the release/checkpoint notes. A failed
hash, missing Windows wheel, `pip check` conflict, or changed CUDA behavior is
an environment failure, not a reason to loosen pins during a measured run.
