# T17 — Binary metric implementation review

## Assignment

Review an implementable binary ROC-AUC and log-loss design for the Churn
experiment without adding a heavyweight metrics dependency. This note is a
design/API and test contract for the implementation owner; no source module was
changed by T17.

## Sources and evidence

- The scikit-learn `roc_auc_score` documentation describes binary AUC as the
  area of the ROC curve and accepts a score/ranking rather than requiring a
  calibrated probability. The implementation below uses the equivalent
  Mann–Whitney probability-of-correct-ranking definition, including half credit
  for ties. Reference: <https://scikit-learn.org/stable/modules/generated/sklearn.metrics.roc_auc_score.html>.
- The scikit-learn `log_loss` documentation gives the binary negative
  log-likelihood formula and clips probabilities to a dtype-dependent machine
  epsilon. Reference: <https://scikit-learn.org/stable/modules/generated/sklearn.metrics.log_loss.html>.
- A local exhaustive Python oracle check covered every binary label sequence of
  lengths 2–5 containing both classes and all score sequences over
  `{0.0, 0.5, 1.0}`: 8,604 AUC cases passed. Named tie/reversal/ordering cases,
  log-loss cases, and single-class checks also passed. No project test suite or
  training was run because the repository had no source yet.

## Recommended API contract

Keep the public metric surface small and dependency-light (standard-library
sorting/math is sufficient; callers may pass detached model outputs converted
to ordinary sequences):

```python
def binary_roc_auc(y_true, y_score) -> float:
    """Return binary ROC-AUC; raise ValueError for an undefined input."""

def binary_log_loss(y_true, y_prob, *, eps=None) -> float:
    """Return mean binary cross-entropy after probability clipping."""
```

Input requirements for both functions:

1. `y_true` and the prediction sequence are one-dimensional, non-empty, and
   have equal lengths.
2. Labels are exactly binary `0`/`1` (booleans may be normalized to those
   values). Reject other labels instead of guessing a positive class.
3. Values are finite. Reject NaN/positive or negative infinity before sorting or
   clipping; NaN ordering is otherwise implementation-dependent.
4. Return an ordinary finite `float` whenever the inputs pass validation.

`binary_roc_auc` accepts probabilities, logits, or any other finite real
**scores**, because AUC only depends on ordering. `binary_log_loss` accepts
positive-class **probabilities** in `[0, 1]`; keep a separate logits-to-loss
function if one is ever needed rather than silently interpreting logits as
probabilities. Probability endpoints 0 and 1 are allowed and clipped for a
finite metric.

## ROC-AUC formula and implementation

For positive scores `s+` and negative scores `s-`,

\[
  AUC = \frac{1}{n_+ n_-}\sum_{i:y_i=1}\sum_{j:y_j=0}
       \left[1(s_i>s_j)+\tfrac12 1(s_i=s_j)\right].
\]

Do not enumerate all positive/negative pairs. A simple `O(n log n)` and `O(n)`
algorithm is:

1. Sort `(score, label)` in ascending score order and process one equal-score
   group at a time.
2. Maintain `negatives_before`, the count of negative samples in lower-score
   groups. For a group with `p_g` positives and `n_g` negatives, add
   `p_g * negatives_before + 0.5 * p_g * n_g` to `wins`.
3. Add `n_g` to `negatives_before` and continue. Return
   `wins / (n_pos * n_neg)`.

Grouping equal values is essential: sorting individual records and assigning
arbitrary rank order incorrectly gives ties all-wins or all-losses. An
equivalent rank-sum implementation is `U = sum(average_rank_of_positive) -
n_pos*(n_pos+1)/2`, then `U/(n_pos*n_neg)`; either version must award half credit
to cross-class ties.

Validation and single-class behavior:

- If `n_pos == 0` or `n_neg == 0`, raise `ValueError` with a clear message such
  as `ROC-AUC requires both classes`. AUC is mathematically undefined; do not
  return `0.5`, `0`, or NaN.
- An empty input, length mismatch, nonbinary label, or nonfinite score should
  raise `ValueError` (or the project's established input-validation exception)
  before the denominator or sort is used.
- Stable sort is not required once equal-score groups are explicitly consumed.
  Exact equality should be used after conversion to the chosen scalar type;
  do not introduce an arbitrary tolerance that changes the ranking.

This behavior is important for checkpoint/greedy selection: a malformed or
single-class validation split should be surfaced by preflight rather than
silently making a candidate look like a 0.5-AUC candidate.

## Binary log-loss formula and implementation

For a positive-class probability `p_i`,

\[
  logloss = -\frac1n \sum_i [y_i\log(p_i) + (1-y_i)\log(1-p_i)].
\]

Clip each probability first:

```text
q_i = min(max(p_i, eps), 1 - eps)
```

Use natural logarithms. For this reduced experiment, recommend converting
metric inputs and probability-averaging accumulators to float64 and resolving
`eps=None` to `sys.float_info.epsilon = 2**-52` regardless of training dtype.
This fixes evaluation semantics across float32 tensors and Python lists and
matches float64 machine-epsilon clipping. This is a proposal, not a claim that
the paper uses this epsilon. Do not silently use float32 epsilon in one method
and float64 epsilon in another. Validate an explicit epsilon as finite,
`0 < eps < 0.5`, and representable such that `0 < eps < 1-eps < 1`; values so
small that `1-eps` rounds to 1 cannot safely implement two-sided clipping.
Reject probabilities below 0 or above 1 rather than silently clipping
out-of-range model bugs. Compute
`-log(q_i)` for label 1 and `-log1p(-q_i)` for label 0; `log1p` is more accurate
near zero. Use compensated summation (`math.fsum`) in a Python implementation.

Unlike AUC, log-loss remains defined when the observed labels contain only one
class, so do not reject a single-class sequence here. Empty input, length
mismatch, nonbinary labels, nonfinite probabilities, and out-of-range
probabilities should still raise. With `normalize=False` as an optional future
extension, return the sum; the experiment should use the normalized mean.

For an ensemble, average member probabilities first, then calculate both
metrics on that final probability vector. Do not average per-member log-losses
or AUCs when reporting ensemble metrics; neither operation equals evaluating
the ensemble. Average probabilities, not logits. Clip only the final averaged
probability for log-loss; never clip the input used for AUC because clipping
can create additional ties.

## Focused test cases

The eventual metric tests should include the following exact expectations (up
to ordinary floating-point tolerance):

### AUC

| labels | scores | expected/result |
| --- | --- | --- |
| `[0, 1]` | `[0.1, 0.9]` | `1.0` |
| `[0, 1]` | `[0.9, 0.1]` | `0.0` |
| `[0, 1]` | `[0.5, 0.5]` | `0.5` (cross-class tie) |
| `[0, 1, 0, 1]` | `[0.1, 0.4, 0.4, 0.8]` | `0.875` (tie gets half credit) |
| `[0, 1, 0, 1]` | `[0.5, 0.5, 0.5, 0.5]` | `0.5` (all ties) |
| `[0, 0, 1, 1]` | `[0.1, 0.2, 0.3, 0.4]` | `1.0` |
| `[0, 0, 1, 1]` | `[0.1, 0.4, 0.35, 0.8]` | `0.75` |

Also assert `ValueError` for `[]`, `[0, 0]`, `[1, 1]`, unequal lengths,
nonbinary labels, and scores containing NaN or infinity. A property test/oracle
can compare the grouped algorithm with the explicit pair formula on small
inputs; the local exhaustive check above is a suitable reference.

### Log-loss

| labels | probabilities | expected/result |
| --- | --- | --- |
| `[0, 1]` | `[0.1, 0.9]` | `-log(0.9) = 0.1053605156578263` |
| `[0, 1]` | `[0.5, 0.5]` | `log(2) = 0.6931471805599453` |
| `[1, 1]` | `[0.8, 0.6]` | `-(log(.8)+log(.6))/2 = 0.3669845875401002` |
| `[0, 1]` | `[0, 1]` | `-log1p(-eps)`, approximately `2.2204460492503136e-16` for default epsilon |
| `[0, 1]` | `[1, 0]` | `-log(eps) = 36.04365338911715` for default epsilon |
| `[1, 1]` | `[0.2, 0.8]` | valid despite one observed class |

Also assert `ValueError` for empty/mismatched inputs, labels outside `{0,1}`,
NaN/infinity, and probabilities such as `-0.01` or `1.01`. Reject epsilon values
0, negative, 0.5, NaN, infinity, and an unrepresentably small value such as
`1e-300`. Test that endpoint results change consistently with explicit epsilon.
Do not use the usual `1e-12` absolute tolerance for the tiny correct-endpoint
case because that would also accept a falsely hardcoded zero.
