## Recommended checkpoint sequence

Use a few coherent integration commits rather than one commit per agent. The
coordinator alone stages and commits; agents' edits must settle for the paths in
each checkpoint before inspection, validation, and staging.

| Checkpoint | Contents | Evidence required |
| --- | --- | --- |
| C1: foundation | Ignore rules, package/configuration foundation, license/reference attribution, task ledger and reviewed design notes as available | File inventory and content review; explicitly label runtime checks not yet available |
| C2: verified implementation | Integrated models, optimizer, selection, preprocessing, runner/CLI, meaningful tests, reproducible environment definitions and guides | Actual applicable lint/type/test/smoke commands and outcomes; resolve implementation/test disagreements before claiming success |
| C3: measured experiment | Compact real-run results, resolved configurations, source/data/environment provenance and report | Runs tied to the earlier committed implementation, frozen selection before final test, actual measurement/aggregation checks |
| C4: release documentation, if needed | Final README, reconciliation of task findings, checkpoint/verification receipts and limitations | Clean intended release tree, reviewed results claims, final applicable checks |

Combine checkpoints when genuinely coherent. If C2 needs a fix during real runs,
commit that fix as another focused implementation checkpoint before accepting a
new measurement. Retain accurate identities for earlier runs; never relabel their
execution SHA as the later fix or release SHA. Use ordinary concise messages
such as `Add independent packed training and equivalence tests`; there is no
existing commit-message history to follow yet.

## Coordinator commit transaction

1. Before every commit inspect `git status --short --branch`, `git diff`, and
   `git log --oneline -10`. On the initial commit record the expected unborn-HEAD
   failure. Inspect new files explicitly: ordinary `git diff` omits untracked
   contents. Read applicable repository instructions and any hooks' requirements.
2. Review the intended file list and run the checks appropriate to that exact
   content. Coordinate a stable snapshot; other agents may still be editing.
   A test run against different bytes is not a test receipt for the staged tree.
3. Stage explicit reviewed paths, not an indiscriminate `git add .` or `git add -A`
   over active swarm work. Inspect `git diff --cached --name-status`,
   `git diff --cached --stat`, `git diff --cached --check`, and the full staged
   diff. The cached diff works before a first commit and shows additions against
   the empty tree; do not depend on `HEAD^` or `HEAD~1` for the root commit.
4. Commit only this checkpoint with the existing identity/settings and normal
   hooks. If a hook or commit fails, fix the cause, rerun affected checks, and
   make the intended new commit normally. Do not bypass hooks or amend/reset
   earlier history to make the record appear cleaner. If identity is missing,
   ask the user/coordinator for configuration rather than inventing authorship.
5. Verify `git rev-parse HEAD`, `git show --stat --oneline HEAD`,
   `git status --short --branch`, and, when relevant, the full committed diff.
   Record the full SHA, not just the abbreviated display. Untracked residual
   agent work is reported as such; it is not part of that commit.

The present ignore file covers `.venv`, `.reference`, `.cache`, `data`, `runs`,
common caches, `.env` files, logs, and `.pt`/`.npz` artifacts. Keep downloaded
reference code, datasets, virtual environments, and large model files outside
release commits. Retain compact, reviewed result summaries and manifests in a
tracked location such as `results/`; an ignored `runs/` directory by itself is
not a reproducible published result. Check explicit output paths with
`git check-ignore -v` when needed. Ignore rules do not replace staged-content
review and do not remove files already tracked.

## Requested remote and publication

- **Coordinator action required:** retrieve the exact target URL from the user's
  original instruction and retain a credential-free repository identity in the
  checkpoint record. Do not infer it from this directory name or the official
  `yandex-research/tabpack` reference repository.
- Verify current local remotes and the target's current advertised refs before
  publication. The earlier empty-ref observation can become stale while agents
  work. A successful read only proves read access at that moment. Record the
  observation time and outcome, including an empty result or authentication error.
- Configure the requested remote only in the coordinator's authorized workflow.
  If an existing `origin` unexpectedly differs, reconcile it rather than silently
  overwriting it. Keep the current branch name unless a different name was
  requested or deliberately agreed; the observed name is `master`, not `main`.
- A request to set up a remote or create local commits is not by itself a request
  to push. Publish only when the user's instructions authorize pushing. If the
  target remains empty, a normal explicit first push such as
  `git push --set-upstream origin <agreed-branch>` creates that branch. No force
  option is necessary. Do not push every local branch or create tags implicitly.
- If the remote acquired history, stop to inspect ancestry and reconcile the
  intended workflow. Do not force-push, delete refs, or import unrelated history
  merely to make the command succeed. A rejection is a recorded blocker.
- After an authorized push, verify the remote branch SHA with
  `git ls-remote --heads origin refs/heads/<agreed-branch>` against local HEAD,
  and verify upstream tracking. Record success only after that verification.
  A remote branch's existence does not prove hosting-service CI passed or that
  it became the service's default branch. Record those separately if relevant.

## What `docs/checkpoints.md` should contain

For each checkpoint, record:

1. Stable checkpoint ID, UTC timestamp, purpose, scope/paths, branch, and parent
   full SHA; use `null`/`unborn_repository` for C1's parent.
2. Contributing task IDs and note paths, coordinator integration/review work, and
   deviations resolved. Attribute agents as task contributors; do not fabricate
   human names, emails, signatures, or `Co-authored-by` identities.
3. Exact verification commands, relative working directory, interpreter/environment
   identity, exit outcomes and meaningful pass/fail/skip counts. Record unavailable
   checks honestly, with reason. Link sanitized retained evidence when useful.
4. Full implementation SHA actually executed, source-inventory hash, resolved
   config/data identities and run IDs for measurements; separately identify the
   commit that later adds the report. Record staged/unstaged/untracked state at
   measurement time and why any residual files cannot affect execution.
5. Full resulting commit SHA and verification outcome; approved remote identity,
   local/remote branch, observed remote SHA, publication timestamp and outcome
   when published. If publication was not requested, say `not requested`; if it
   failed, preserve the real error category and local completion state.
6. Limitations and unresolved integration findings, including any missing run,
   budget change, unavailable dataset, skipped device, or unmet release gate.

**Avoid a self-referential commit receipt.** A tracked file cannot contain the
SHA of the very commit that first stores those same bytes. Put the planned
checkpoint ID and validation evidence in its commit, then add its resulting SHA
to the next checkpoint's record. The final checkpoint's full SHA can be reported
in the coordinator's final handoff and Git history; do not repeatedly amend it
trying to store its own hash. Likewise, provenance captures the pre-run code SHA,
not the unknown future commit that will contain the generated results.
