# T41 — CLI acceptance specification

## Assignment

Specify a small, reproducible command-line contract for the Churn experiment's
`preflight`, `dry-run`, `run`, and `report` commands. This is a design note for
the implementer; no source, dependency, or training changes were made.

## Sources and constraints

- The task ledger (`swarm.md`) is the source for the current reduced protocol:
  seeds `[0, 1, 2]`, four base members, maximum selected ensemble size four,
  100-epoch cap, patience 16, batch size 256, float32, and the baseline and
  heterogeneous search spaces recorded there.
- The ledger requires canonical Churn train/validation/test splits and
  train-only preprocessing. It explicitly prohibits silently substituting IBM
  Telco or synthetic data, and requires test evaluation only after selection is
  frozen.
- The coordinator's finding records Windows/Python/CUDA variability. Every
  command therefore needs an explicit resolved device in its diagnostics and
  must support CPU execution.
- Related notes read before completion: T27 (architecture), T42 (synthetic
  integration smoke), T43 (preflight tests), T20 (report schema), and T35
  (checkpoints). Reconciliation is recorded under Coordination below.

## Canonical invocation

The proposed executable is `python -m tabpack.cli`; packaging does not yet
exist, so these are acceptance examples, not currently runnable commands. If a
console entry point is added, it must expose an equivalent interface, not a second
behavioral contract. Examples below use a local dataset and the reduced config:

```text
python -m tabpack.cli preflight --config configs/churn_reduced.yaml --data-root data/churn --run-dir runs/churn-reduced --device cpu
python -m tabpack.cli dry-run   --config configs/churn_reduced.yaml --data-root data/churn --device cpu
python -m tabpack.cli run       --config configs/churn_reduced.yaml --data-root data/churn --run-dir runs/churn-reduced --device cpu
python -m tabpack.cli report    --run-dir runs/churn-reduced --format markdown --output reports/churn-reduced.md
```

`--config` is required for `preflight`, `dry-run`, and `run`; `report` reads
the immutable manifest in `--run-dir` and does not need a config or dataset.
Paths are interpreted relative to the current working directory, resolved to
absolute paths in local diagnostics. Public artifacts use bundle-relative
paths and sanitized command/config origins rather than absolute home paths.
A path must not be silently redirected to a default dataset.

## Shared options

| Option | Commands | Contract |
| --- | --- | --- |
| `--config PATH` | preflight, dry-run, run | YAML/JSON experiment config. It is parsed and schema-validated before any model or data work. |
| `--data-root PATH` | preflight, dry-run, run | Optional path override for the dataset root. If omitted, use the config value. The resolved value is recorded. |
| `--run-dir PATH` | all | Required by `run`; optional for preflight/dry-run; required by report. It is the run artifact directory, not a cache. |
| `--device auto\|cpu\|cuda` | preflight, dry-run, run | Default `auto`. Resolve and print the actual device. Explicit `cuda` fails rather than falling back when CUDA is unavailable. |
| `--seeds LIST` | preflight, dry-run, run | Comma-separated integers in `[0, 2^32-1]`, defaulting to the config's `[0,1,2]`; reject empty tokens, duplicates, and out-of-range values; preserve declared order in the manifest. |
| `--families LIST` | preflight, dry-run, run | Comma-separated subset of `ordinary`, `independent`, and `packed`; default is all three. A subset is marked as a partial comparison. |
| `--num-workers N` | preflight, dry-run, run | Non-negative data-loader worker count, default `0` for portable Windows behavior; record it. |
| `--json` | preflight, dry-run, run, report | Emit the command result as one JSON document to stdout. Human diagnostics/progress go to stderr. JSON has `schema_version`, `ok`, `command`, `status`, `errors`, `warnings`, and `resolved`/`artifacts` as applicable. On report this aliases `--format json`; conflict with an explicit non-JSON format is usage error 2. |
| `--strict` | preflight, dry-run, report | Treat warnings (including partial/noncanonical protocol warnings) as failures. It does not hide the underlying diagnostic. |
| `--help`, `--version` | all | Return zero without touching the dataset, run directory, network, or checkpoints. |

The config is the scientific source of truth. There is no free-form
`--override` option. `--seeds`, `--families`, device, and worker count are the
only run-shaping command-line overrides and must be copied into the manifest.
Configuration changes are supported without a second approval flag, but every
effective value must be recorded. A noncanonical or partial run is labelled
in every report. Here `canonical` means the currently agreed **local reduced
protocol**, never paper-equivalence; print the full reduced TabPack-style
optimistic-evaluation label even for a canonical local run.

## `preflight`

### Purpose and options

`preflight` is a safe diagnostic. It validates the requested experiment without
training, model checkpoint creation, test inference, or network access.

```text
preflight [shared options] [--write-report PATH]
```

`--write-report PATH` is optional. Without it, preflight writes no files; with
it, it atomically writes the same JSON object printed by `--json` (or a JSON
report regardless of console format). It must not create a run manifest or
delete an existing file unless an explicit `--overwrite` option is added by
the implementer.

### Required checks

The check is ordered so a missing configuration is reported before expensive
data inspection:

1. Parse and schema-validate config, including binary target, family names,
   member counts, epoch/patience/batch limits, dtype, and optimizer fields.
2. Check Python/package versions and importable torch before data loading or
   device-dependent probes. Missing torch produces `TORCH_MISSING` and marks
   dependent checks skipped. Never import torch unconditionally while parsing
   `--help`, `--version`, or an artifact-only report.
3. Resolve the dataset path and verify the declared canonical Churn source,
   expected files, provenance/fingerprint metadata, and readable permissions.
   A missing or unverified dataset is an error with an actionable path; IBM
   Telco, synthetic, or another unrecognized source is never substituted.
4. Verify train/validation/test split presence, target availability, binary
   labels with both classes, non-empty rows, and disjoint IDs where authoritative
   row IDs exist. When they do not, rely on exact canonical split fingerprints;
   do not invent original IDs or treat equal feature rows as proof of overlap.
   Check that numeric median and
   quantile-normal parameters and categorical imputation/one-hot vocabulary
   are declared as train-fitted only.
5. Check selected device, CUDA availability when requested, float32 support,
   available RAM/disk versus documented requirements, and a writable parent for a
   future run directory. A missing CUDA device is a warning for `auto` and an
   error for explicit `cuda`; explicit `cpu` does not require CUDA. Metadata-only
   preflight cannot prove kernel compatibility: `run` must surface kernel/runtime
   failures and never retry on CPU silently after training has started.
   Report `RAM_LOW`/`DISK_LOW` with required and available bytes when a defensible
   bound is exceeded; unknown estimates are explicit warnings. These probes
   must not allocate model/tensor memory or fill disk. An output-parent
   permission estimate cannot guarantee later successful writes and must be
   labelled as such; preflight does not create probe files by default.
6. Resolve the seed list, family list, deterministic settings, and canonical
   versus noncanonical protocol status. Report all warnings; do not infer
   undocumented defaults.

Each diagnostic carries a stable code, severity, remediation, and structured
facts, using T43's proposed `TORCH_MISSING`, `DATA_MISSING`, `DISK_LOW`,
`RAM_LOW`, and `CUDA_FALLBACK` names where applicable. Independent checks have
a fixed order; blocked dependent checks are marked skipped, never passed.

Success is `status: "ready"` and exit code 0. Warnings still return 0 unless
`--strict` is present. A successful preflight must make it possible for
`dry-run` to proceed with the same arguments. A failed preflight returns no
traceback in normal mode and no training side effect.

## `dry-run`

### Purpose and options

`dry-run` performs preflight and then resolves the complete execution plan. It
does not train, initialize optimizer state, save weights, evaluate test data,
or contact the network.

```text
dry-run [shared options] [--write-plan PATH]
```

The default output is a deterministic human-readable plan. `--json` emits a
machine-readable plan. `--write-plan PATH` is opt-in and atomically writes the
plan; absent that option, no file or run directory is created. A plan is not a
successful run and must never be accepted by `report`.

### Plan contents and acceptance behavior

For every requested seed and family, the plan must show:

- resolved data fingerprint, split row counts, post-preprocessing feature
  count, dtype, device, batch size, and worker count;
- deterministic member IDs and, for each member, depth, width, dropout, lr,
  weight decay, and parameter estimate;
- one base member for ordinary and four each for the two ensembles, maximum
  selected ensemble size four, epoch cap 100,
  patience 16, and checkpoint/selection schedule;
- maximum training steps (early stopping makes actual steps unknown), expected
  artifact paths, and an estimate of memory
  or an explicit `unknown` value (never a fabricated measurement);
- the fact that ordinary, homogeneous independent, and heterogeneous packed
  families are distinct planned conditions; and
- a `canonical`, `partial`, or `noncanonical` protocol label with reasons.

It may fit preprocessing on training data in memory to resolve feature width;
it must not fit on validation/test, save a transformer, or persist a cache.
Use isolated RNG streams for planning and sampling. Compare deterministic plan
fields within the same environment, excluding volatile available-memory facts.

The plan must state that packed execution uses member dimension first, no
parameter sharing, independent member permutations/losses, probability
averaging, and validation ROC-AUC for checkpoint/greedy choices. It need not
instantiate a model merely to estimate parameters. Any failure in preflight
propagates its exit code and prevents plan generation.

## `run`

### Purpose and options

`run` is the only command that trains or evaluates models.

```text
run [shared options] [--resume]
```

Use an explicit smaller config for a short real-Churn diagnostic run and mark
it noncanonical. Synthetic tests use T42's injected loader/internal run-suite
seam, not a production synthetic fallback or `--smoke` dataset switch.

Before training, `run` executes the equivalent of preflight and dry-run. It
refuses to start if either fails. It creates a manifest containing the sanitized
invocation with exact scientific options, resolved config hash, data fingerprint, code/package versions,
device, seeds, families, and protocol label. A non-empty run directory is an
error unless `--resume` is supplied. Resume is allowed only when the existing
manifest matches config/data/protocol/seed/family/source/environment identities
and checkpoint integrity validates; incompatible resume returns the
artifact-conflict code rather than mixing runs. Resume restores only supported
epoch/selection boundaries (T35), not an unverified mid-batch state. Complete
seed/family results are retained; completed campaigns resume as a verified
no-op. Record resumed timing segments as such, not as clean-run timing.

Training acceptance requirements:

1. Ordinary, homogeneous independent, and reduced heterogeneous packed
   conditions use the same split/preprocessing and requested seed list.
2. Every member has an independent initialization and data permutation. Packed
   loss is averaged over samples and summed over members; no parameter sharing
   is introduced.
3. Checkpoint and greedy decisions use validation ROC-AUC only. The candidate
   pool contains current-epoch members and prior selected checkpoint snapshots;
   selection is without replacement and strictly improving.
4. Test predictions and test metrics are produced only after checkpoint and
   ensemble selection are frozen. A run with an incomplete seed/family is not
   `complete` and cannot be reported as a full comparison.
5. Writes are atomic and resumable where checkpoints are used. Interruption
   leaves T20's explicit `cancelled` or `failed` artifact status with a reason
   and never claims success.

On success, the run directory contains a complete manifest, per-seed/family
metrics and provenance, frozen-selection metadata, predictions or their
documented hash, and a summary suitable for `report`. Output ordering is
stable. A run must not download data implicitly; acquisition is a separate,
explicit workflow with provenance validation.

## `report`

### Purpose and options

`report` aggregates completed run artifacts. It does not train, download,
rerun inference, or require the source dataset.

```text
report --run-dir PATH [--format markdown|json|csv|text]
       [--output PATH] [--strict] [--allow-incomplete] [--overwrite] [--json]
```

`--format` always defaults to `markdown`, including redirected output, so
shell context cannot change the schema. `--output` defaults to stdout. Existing output files are protected;
`--overwrite` is required to replace one. `--allow-incomplete` is diagnostic
only: it emits excluded-run details and never presents incomplete artifacts as
valid observations. With `--strict`, incomplete/mixed/noncanonical inputs
fail instead of producing a partial report.

Report validation rejects unknown schemas, malformed metrics, inconsistent
hashes, ambiguous duplicate logical runs, mismatched datasets, and test metrics
recorded before selection freeze. These integrity errors remain fatal with
`--allow-incomplete`. That flag only permits missing/failed/cancelled expected
seed/family results to be excluded with an explicit incomplete diagnostic.
Duplicate **snapshot IDs** are invalid; the same member ID at different epochs
is valid and must survive reporting. Never silently merge incompatible protocol
labels. A complete noncanonical local run may be reported with its label;
`--strict` rejects its warning by design.

The result has one observation per accepted seed × family, plus aggregate
count/mean/sample-standard-deviation fields (`ddof=1`; `null` for one seed).
Selected snapshots are nested detail/a separate table, never extra observations.
CLI family aliases map to T20's stable method identifiers: `ordinary` → `mlp`,
`independent` → `independent_mlp_ensemble`, and `packed` →
`packed_heterogeneous_ensemble`. JSON retains full precision; presentation rounds
only after aggregation. The output
must include validation ROC-AUC used for selection and the final test metrics
declared by the config, with the protocol label and provenance identifiers.
JSON keys and CSV/Markdown row ordering follow T20: declared method order,
numeric seed, attempt, and run ID. Numeric formatting is locale-independent.
For a single `--format csv` output, emit T20's `summary.csv` schema; the detailed
run and selection tables remain available through JSON/Markdown. Timing,
selection counts, provenance hashes, failed/excluded runs, expected/complete
counts, and the reduced-protocol limitation label are required report content.

## Exit codes and machine-readable errors

The implementation should keep these stable across commands:

| Code | Meaning |
| ---: | --- |
| 0 | Requested command completed successfully. Warnings may be present unless `--strict`. |
| 2 | CLI usage or config/schema error (including malformed option values). |
| 3 | Environment, dependency, device, permission, dataset/preflight failure, or strict preflight/dry-run warning failure. |
| 4 | Existing/incompatible artifact or protected output path conflict. |
| 5 | Training/runtime interruption or execution failure; run status is not complete. |
| 6 | Report input is incomplete, inconsistent, unverifiable, malformed, or fails strict warning policy. |
| 130 | User interrupt if the process is terminated by Ctrl-C before a normal command result can be emitted. |

For `--json`, failures use a shape like:

```json
{
  "schema_version": 1,
  "ok": false,
  "command": "preflight",
  "status": "failed",
  "errors": [{"code": "DATA_MISSING", "severity": "error", "message": "...", "remediation": "...", "facts": {"path": "..."}}],
  "warnings": [],
  "resolved": {}
}
```

The command envelope and T20 artifact objects are distinct schemas; document
which is returned and embed the report data under a stable `report` key in the
JSON envelope. Native parser failures must honor `--json` as well as runtime
failures. `--help`/`--version` take precedence and keep their ordinary text.
Output serialization/write failure is nonzero, even if calculations succeeded.
Normal mode prints the concise message and remediation to stderr; it should
not expose a Python traceback for expected user/config/data errors.

## Acceptance checklist for implementation and CI

1. Each command's `--help` and `--version` return 0 without data access.
2. A missing config, malformed config, missing dataset, and explicit unavailable
   CUDA each produce the documented nonzero code and actionable diagnostic.
3. CPU preflight succeeds when the rest of the environment/data are valid,
   regardless of CUDA availability.
4. Dry-run's scientific plan is deterministic across repeated invocations and
   leaves no model, checkpoint, test metric, or run artifact. Its explicit write
   option writes only the plan.
5. Run refuses an incompatible existing directory, records all resolved
   inputs, and does not expose test metrics until selection is frozen.
6. Report rejects incomplete/mixed artifacts by default, handles explicit
   diagnostic exclusion, and emits stable Markdown/JSON/CSV output.
7. A canonical three-seed run is labelled canonical; a seed/family subset,
   synthetic internal smoke run, or changed protocol is visibly labelled partial/noncanonical in
   both manifest and report.

## Tests run

None. The repository has no CLI or test implementation yet, and this task is
research/design only. The checklist above is intended to become focused CLI

## Integration advice and coordination

Implement the parser and result schema before wiring training. Keep the
preflight result reusable by `dry-run` and `run`, and keep `report` artifact
only so it remains useful on a machine without the training environment. The
CLI should expose the reduced protocol through config, while making every
command-line deviation explicit in the manifest.

- **T27 read and incorporated:** the plan retains no-sharing/member-axis/summed
  loss semantics and the report's reduced TabPack-style qualification.
- **T20 read and incorporated:** CLI aliases map to its method identifiers;
  artifacts retain full precision, sample SD, explicit missingness, retry
  ambiguity checks, and snapshot rather than member-ID uniqueness.
- **T35 read and incorporated:** resume validates lineage/integrity and restores
  supported boundaries; partial invocation timings are not clean-run timings.
- **T42 read and incorporated:** expose the same internal run-suite function
  used by `run` to an injected split loader for offline synthetic tests. Keep
  their synthetic provenance and never pass them through canonical Churn
  acceptance as if they were real data. Exact Python API spelling is the
  coordinator's implementation choice.
- **T43 / T19 directed reconciliation:** this proposal uses `--device auto`
  for CPU fallback and treats explicit `--device cuda` as a requirement. T43's
  original requested-CUDA fallback test should either target `auto` or require
  a separately agreed explicit fallback option. Its complementary no-fallback
  test maps to explicit `cuda`. Preflight itself never calls training; test
  downstream CPU selection through the run adapter. Please settle this once
  before wiring tests so help, diagnostics, and behavior agree.
- **Coordinator / T28 / T49:** confirm the package entry point and config
  filename/format (currently proposed, not implemented), then use identical
  examples in the reproduction guide and PowerShell quickstart.
