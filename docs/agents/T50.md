# T50 — Scientific and engineering acceptance gate

## Assignment and release rule

This note defines the gate for calling the reduced Churn experiment a **final
release**. It is a release contract, not evidence that the current repository
has already passed it. A release is final only when every mandatory item below
has a recorded artifact, command, or reviewer sign-off. A failed, missing, or
unreproducible mandatory item makes the result a release candidate (or blocked),
not a final scientific result. Known limitations can be accepted when they are
explicitly disclosed; undisclosed limitations are a gate failure.

The gate applies to all three compared paths:

1. one ordinary MLP;
2. a homogeneous ensemble of independently parameterized MLPs; and
3. the reduced heterogeneous packed TabPack-style ensemble.

The experiment must be described as a reduced, independently authored,
Churn-only experiment. It must not be presented as an official TabPack
implementation, a paper-equivalent reproduction, or a paper result.

## Evidence packet

The coordinator should assemble one release evidence packet and link it from
the final documentation. It should contain, at minimum:

- the exact source Git commit used for each measured run;
- the resolved environment/dependency record and hardware/device record;
- the immutable experiment configuration, seed list, and complete run manifest;
- data source, license, retrieval date, and raw/split/processed hashes;
- preprocessing-fit metadata showing that only training rows fitted transforms;
- per-seed, per-model result files and the aggregate report;
- selected member/checkpoint IDs and validation-selection traces;
- test-only final evaluation records, resource measurements, and failure logs;
- commands used for preflight, tests, training, and report generation; and
- the Git checkpoint table and release reviewer sign-off.

The packet must contain real values from local runs. Placeholder values,
silently omitted failures, or metrics copied from the paper do not satisfy the
gate.

## Mandatory acceptance gates

| Gate | Pass condition | Required evidence | Blocker examples |
| --- | --- | --- | --- |
| Scope and claims | The report names the reduced protocol and distinguishes local measurements from official/paper results. | Protocol/config section and result-table labels | Calling a reduced score “TabPack” or implying paper equivalence |
| Tests and invariants | Relevant automated tests pass in a clean environment; no known regression is waived without a documented issue and release decision. | Test command, dependency record, complete output, and commit SHA | Failing packed/independent equivalence, leakage, metric, selection, or aggregation test |
| End-to-end path | A short deterministic smoke path completes on CPU using test-only synthetic data; the real-data preflight and configured experiment path complete without bypasses. | Smoke/preflight/run manifests and logs | Only a notebook/manual path works, or synthetic data is reported as real data |
| Reproducibility | A fresh rerun from the recorded commit and environment reproduces the fixed-seed smoke result and the measured protocol within stated numeric tolerance. | Two run manifests, commands, versions, seeds, hashes, and comparison report | Missing seed/config, unrecorded rerun, unexplained metric drift, or dirty source |
| Data provenance | The canonical Churn source/splits are identified, legally usable, hash-recorded, and independently verifiable. | URL or acquisition source, license/attribution, retrieval date, hashes, schema, split counts | Unknown data origin, silent IBM/synthetic substitution, or altered split without disclosure |
| Leakage prevention | Preprocessing is fit only on train; validation drives checkpoint/greedy selection; test labels are read only after selection is frozen. | Fit-index metadata and selection/test chronology in the manifest | Test-informed preprocessing, tuning, checkpoint choice, or early stopping |
| Result completeness | Every configured seed and every model family has a success or diagnosed failure record, with per-seed metrics and aggregate statistics. | Per-run table plus mean/std (and n) across seeds | Missing seed/model, cherry-picked rerun, aggregate without per-seed values |
| Fair comparison | Ordinary, homogeneous, and packed paths use the declared common split, budget, metric, and selection rules; deviations are visible. | Resolved config and comparison table | Different data, hidden tuning, or an unreported budget/aggregation change |
| Documentation | A new reader can reproduce the result and understand architecture, data, protocol, outputs, deviations, and limitations. | README/reproduction, architecture, dataset/provenance, CLI, and limitations docs | Results without commands, data card, or explanation of reduced semantics |
| Git checkpoint | Measured code, configuration, reports, and docs are auditable at focused commits with a clean final tree. | `docs/checkpoints.md`, commit SHAs, status/diff review | Untracked required artifacts, post-run source edits, or unverifiable results |

All rows are mandatory for a final release. “Pass” means the evidence is
available to another reviewer, not merely that the author believes the code is
correct.

## Test and numerical acceptance detail

The test suite should cover the following contracts before any full result is
accepted:

- packed forward predictions match separately evaluated member predictions for
  homogeneous and at least one heterogeneous case;
- packed optimizer updates match independent AdamW member updates, including
  member-specific hyperparameters where supported;
- member loss is averaged over samples and summed over members, rather than
  silently averaged over the member axis;
- member parameters, optimizer state, dropout/RNG streams, and training
  permutations are independent (no accidental shared storage or masks);
- preprocessing never learns from validation/test rows, and unknown categories
  follow the documented behavior;
- binary metric values match a trusted reference on ties, degenerate labels,
  and ordinary inputs;
- greedy selection is validation-only, without replacement, strictly
  improving, and records member-plus-epoch snapshot identity;
- probability averaging is performed after sigmoid and only over the frozen
  selected set; and
- result aggregation preserves all seeds, model labels, errors, and resource
  fields without silently dropping failed runs.

The smoke test may use deterministic synthetic data, but that data must be
marked `synthetic_test_only` and must never enter the reported Churn result.
For a deterministic smoke rerun, fixed inputs, seed, configuration, and device
should yield identical selected snapshot IDs and numerically identical output
within the documented backend tolerance. A CUDA rerun may use a separately
documented tolerance; it must not be used to excuse an unexplained CPU
non-reproducibility.

## Reproducibility protocol

The final report must expose the resolved values rather than relying on
defaults. At minimum record Python, package and accelerator versions; operating
system; CPU/GPU, device, and dtype; worker/determinism settings; source commit;
configuration hash; data and split hashes; preprocessing state hash; all seeds;
run start/end times; and the exact commands. The reduced provisional protocol
currently calls for seeds `[0, 1, 2]`, four base members, at most four selected
members, up to 100 epochs, patience 16, batch size 256, and float32. If these
values change, the resolved configuration and rationale must change with them.

Reproduction requires:

1. create/use the documented clean environment;
2. obtain or verify the exact data and hashes;
3. run the documented preflight and tests;
4. run the exact recorded configuration for every declared seed; and
5. regenerate the report from saved run artifacts without hand-editing metrics.

The report should state whether the rerun reproduced exact artifacts, exact
selection, or only metric values within tolerance. Statistical variability
across the declared seeds is expected and must be reported as per-seed values
plus an aggregate (at least mean, standard deviation, and `n`), never hidden
behind one favorable seed.

## Data and result completeness

The data record must identify the canonical source and train/validation/test
split semantics. It must include row counts, feature schema, target encoding,
class counts, missing-value handling, and checksums for downloaded/raw and
materialized data. Numeric median imputation and quantile normalization, and
categorical most-frequent imputation and one-hot encoding, must be demonstrably
fit on train only. If the canonical source or split cannot be verified, the
real-data release is blocked; synthetic data can satisfy only the smoke gate.

For each seed and model family, the result record must include:

- resolved hyperparameters and member sampling;
- training status, epoch/checkpoint, and any early-stop reason;
- validation ROC-AUC trace or summary used for checkpoint/greedy decisions;
- final selected snapshot/member IDs and selection order;
- untouched-test ROC-AUC (and every additional declared metric) only after
  selection was frozen;
- parameter/member counts and optimizer-state accounting;
- wall-clock, peak memory/VRAM when measured, device, and batch details; and
- errors, retries, or exclusions with an explicit reason.

The aggregate must retain the full per-seed table and state the denominator.
An incomplete or failed seed is a reported outcome and a final-release
blocker unless the protocol explicitly defines it as an allowed missing run;
there is currently no such allowance in the reduced three-seed decision.

## Documentation and Git checkpoint gate

The release documentation must link or incorporate the reproduction guide,
architecture semantics, dataset/provenance card, CLI/config contract, results
schema, and scientific limitations. It should explicitly repeat that online
selection is validation-based and that final test evaluation occurs after the
selected set is frozen. The architecture note reviewed for this task already
identifies the important `[M, B, ...]` member-axis, loss-reduction, and
probability-averaging contracts; implementation-specific details must agree
with it.

The coordinator should record focused checkpoints in `docs/checkpoints.md`, for
example:

1. implementation and unit-test checkpoint;
2. integration/preflight checkpoint;
3. measured-run checkpoint containing source/config/data hashes; and
4. final report/documentation checkpoint.

Each entry should list the commit SHA, scope, tests and environment used, and
the artifact paths it validates. Before declaring final, inspect the complete
diff and `git status`; required source, docs, configs, and evidence artifacts
must be committed, no secret or private local log may be included, and the
measured run must point to an immutable source SHA. A release tag is useful but
does not replace the checkpoint table or evidence packet.

## Explicit limitations that must ship with the result

The final report must state, in plain language, at least these boundaries:

- this is a Churn-only, reduced experiment with three provisional seeds and a
  small member/budget count, so uncertainty and external validity are limited;
- the packed heterogeneous path is TabPack-style and independently authored,
  not the official implementation or a paper-equivalent protocol;
- periodic feature embeddings, Muon, base pruning, official-scale search, and
  any other omitted paper features are not evaluated unless separately added;
- validation-driven checkpoint and greedy selection can make results
  optimistic relative to an untouched external evaluation;
- any hardware, backend, runtime, or CUDA timing comparison is specific to the
  recorded environment and is not a universal speed/memory claim; and
- a result demonstrates the stated local protocol only, not production
  readiness, causal benefit, or superiority on untested datasets.

Limitations do not invalidate the release when the scope and claims remain
aligned with them. A claim that exceeds the protocol is a scientific gate
failure even if all software tests pass.

## Final sign-off checklist

The coordinator can copy this checklist into the release review:

- [ ] Scope wording and claim boundaries reviewed.
- [ ] Clean-environment unit, integration, and smoke tests pass.
- [ ] Fixed-seed reproducibility rerun and tolerances recorded.
- [ ] Canonical data, license, split, preprocessing, and hashes recorded.
- [ ] Leakage chronology verified; test is untouched until selection freezes.
- [ ] All three model paths, all configured seeds, and all failures represented.
- [ ] Per-seed metrics, aggregate statistics, selected snapshots, and resource
      accounting are complete.
- [ ] Reproduction, architecture, dataset, CLI, provenance, and limitations
      documentation are linked and internally consistent.
- [ ] Focused Git checkpoints, source SHAs, complete diff, and clean status
      reviewed; no secrets or private artifacts included.
- [ ] A reviewer signs the evidence packet and assigns `FINAL`, `RC`, or
      `BLOCKED`.

Only `FINAL` satisfies the user's final-release request. `RC` must identify the
missing gate and remain clearly labeled; `BLOCKED` must identify the failure
and cannot be reported as a scientific result.
